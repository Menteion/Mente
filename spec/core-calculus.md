# The Core Calculus

**Governs:** `compiler/mente-syntax`, `compiler/mente-sema`, `compiler/mente-mir`, `compiler/mente-codegen` and the reference interpreter `mente-interp`

This file is normative for the language of milestones M1 and M2 ([`core-calculus-home`](../docs/design-review.md#core-calculus-home)). It says which programs each accepts, what they compute, and when they trap. The reference interpreter implements it rule by rule; the conformance suite tests it; MIR and native code must agree with it, since the three execution paths are compared (`ROADMAP.md`, M1). Each milestone extends it before any of its code: items 1 to 10 are M1's language, which the compiler implements, and items 11 to 23 extend it to M2's, written in M2's design closure ([`m2-design-closure`](../docs/design-review.md#m2-design-closure)). Item 24 sorts the constructs into a kernel, whose rules are its own, and elaborations, each defined by its translation into the kernel ([`elaboration-to-core`](../docs/design-review.md#elaboration-to-core)). Item 25 gives a run its stack budget, which the three execution paths count alike ([`stack-budget`](../docs/design-review.md#stack-budget)). Its concrete syntax is in `grammar.md`; where another spec file says more about a mechanism, this file states only what the milestone takes from it.

## 1. Specification

1. `Specified` **What M1 contains**: integers, `bool`, fixed-size arrays `[N]T` held as values, functions with read-only and `mut` parameters, `val` and `var`, `if`, `while` with `break` and `continue` ([`loop-exits`](../docs/design-review.md#loop-exits)), `guard`, `return`, `requires` and `ensures`, refined integer types, `todo` and `unreachable`.
   - A program that uses anything else (structs, enums, `?T`, `T ! E`, effects, floating-point and fixed-point values, units, `own` and `in` parameters, views, generics, traits, `comptime`, `wrap<T>` and `sat<T>`, parallelism) is rejected with a diagnostic that names the construct and the milestone that brings it. Those mechanisms stay specified in their own files.
2. `Specified` **Integer types are ranges** ([`integer-conversions`](../docs/design-review.md#integer-conversions)):
   - An integer value is a mathematical integer. An integer type names a range of them: `uN` holds `0 ..= 2^N - 1` and `iN` holds `-2^(N-1) ..= 2^(N-1) - 1`, for `N` in 8, 16, 32, 64 and 128. On every M1 target `usize` is 64 bits wide and unsigned.
   - There are no conversions between integer types. Any integer expression may flow into any integer type, and is checked where it is narrowed (item 4).
   - A refined type `T[a..b]` or `T[a..=b]` names the part of `T`'s range inside the interval. Its bounds are integer literals or names of bindings that cannot change in the refined value's scope: a `val` or a read-only parameter, or `.len` of an array (`refinement-and-fixed-point.md`, item 1). `T[a..b]` is a subtype of `T`.
   - A plain type is a range checked at run time where Tier 1 cannot prove it; a refined type is a range proven at compile time (item 8).
   - `Implemented`: the type checker treats integer types as ranges, so any integer value flows into any integer type, and suggests for operands of two types the smallest standard type that holds both.

3. `Specified` **`bool` and arrays**:
   - `bool` holds `true` and `false`. No integer converts to `bool` or back.
   - `[N]T` holds `N` values of type `T`, where `N` is a non-negative integer literal without a suffix, since it is a count and takes no type and `T` is any M1 type, arrays included. `a.len` is `N`. `a.len` is a value its type fixes, not a place: no assignment and no `mut` argument changes it. An index may have any integer type, and is checked against `0 ..= N - 1`. An array is a value: binding, passing and returning it copies it, and no two bindings ever share one.
   - `Implemented`: no integer becomes a `bool`, an array flows only into an array of its length, an index has any integer type, and `.len` of an array is a `usize`; `.len` of a value of no type, such as `todo("a")`, has no type either and gives no value (item 6), and `.len` of anything else is an error (`E0215`).

4. `Specified` **Integer arithmetic is exact, and checked where it is narrowed** ([`overflow-check-cost`](../docs/design-review.md#overflow-check-cost)):
   - `+`, `-`, `*`, `/`, `%` and unary `-` compute the exact mathematical result, whatever the integer types of their operands. `/` truncates toward zero, `%` takes the sign of its left operand, and a zero divisor traps.
   - A value is narrowed, and checked against the type it enters, at a binding's initializer, an assignment, an argument, a returned value, an element of an array literal, an element store, and a `match`'s integer scrutinee, which enters its own type ([`match-scrutinee-narrowing`](../docs/design-review.md#match-scrutinee-narrowing)). A value outside the type's range traps. A scrutinee's narrowing, unlike the others into a plain type, Tier 1 must prove, or the program is rejected (`E0502`), so that the arms, which cover the type, cover every value. An array literal whose elements have one integer type narrows each into it; one whose elements have different integer types keeps them exact until the array lands, where each is narrowed into the place's element type.
   - The bit operations `&`, `|`, `^` and `~` and the shifts `<<` and `>>` are narrowing points too. The operands of `&`, `|` and `^` have one integer type, and the operation works on their two's-complement bits in that type. `x << k` is `x · 2^k`, then narrowed to `x`'s type; `x >> k` is `x / 2^k` rounded toward negative infinity. A shift amount outside `0 ..= width - 1` of `x`'s type traps.
   - An operation with an `i128` or `u128` operand is itself a narrowing point, checked against that type; so `i128` and `u128` arithmetic is checked at every operator.
   - Every other arithmetic operation, a compound assignment's included, has a static range, computed from its operands' ranges. A literal's range is its value, `.len`'s the array's length, a name's its declared refinement's when both bounds are literals, an `if`'s the hull of its branches', and any other integer's its type's range. An operation whose range lies neither within `u128` nor within `i128` is an error (`E0222`), and so is any other place where values meet in one machine type when their hull does not fit one: an `if`'s branches, an operation's operands beside its value, and the integers of an array literal of integers of no one type, those of the array literals nested in it at any depth included. So every intermediate fits one 128-bit machine type, in which native code computes it without a check, and the three execution paths agree on every value ([`wide-intermediates`](../docs/design-review.md#wide-intermediates)).
   - `Implemented`: the checker gives each arithmetic operation of narrower operands its static range and reports `E0222` for one that might leave both `i128` and `u128`, such as `a * a * a` for a `u64`. Its fix binds the operand of larger range to a `u128`, or to an `i128` when the result may be negative, before the statement, or turns an expression body into a block that does; in a loop's condition, which runs every round, it offers none. It reports `E0222` for an `if` whose branches' values fit no one of the two types together, such as an `i64` and a `u128`, and its fix binds the value of the branch that reaches highest to an `i128` inside that branch, where it alone is computed. It reports `E0222` too for an operation whose operands fit no one type with its value, binding the operand of larger range to the type that holds the value, and for an array literal whose elements, of no one integer type, fit no one type together, the integers of the array literals nested in it counted with its own, once.

5. `Specified` **The type of an unannotated binding** ([`integer-inference`](../docs/design-review.md#integer-inference)):
   - `val x = e` and `var x = e` take `e`'s type. When the integer operands of `e` all have one type, `e` has that type, so `a + b` with `a` and `b` of type `u8` is a `u8`, and a sum above 255 traps at the binding.
   - A binding takes a refined type only when it states one ([`refinement-inference`](../docs/design-review.md#refinement-inference)): an expression's type is the plain type of its operands, so with `lo: usize[0..64]`, `val m = lo + 1` is a `usize`. Tier 1 still knows from its facts that `m <= 64`.
   - An integer literal takes the type of the other operands, or of the place it is narrowed into; an expression of literals alone is an `i64`. A literal with a suffix (`255_u8`) has the suffix's type, and its value lies in that type, or reaches the type's smallest value right after a unary `-` (`-128_i8`).
   - When `e`'s integer operands have different types, the binding must state its type. The diagnostic suggests the smallest standard type that holds both operands' ranges: `u32` for a `u8` and a `u32`, `i64` for an `i32` and a `u32`.
   - `Implemented`: an unannotated binding takes its initializer's type, the plain type of its operands, and literals alone make an `i64`; one whose operands have different integer types is an error (`E0212`) whose fix states the type that holds them all.

6. `Specified` **Bindings, blocks and statements**:
   - `val` binds a value that never changes; `var` binds one that assignment may change. A name is declared once in a function, its parameters and inner blocks included ([`no-shadowing`](../docs/design-review.md#no-shadowing)); a second declaration is an error whose fix suggests a new name, and so is a binding named like a function of its module ([`strict-defaults`](../docs/design-review.md#strict-defaults)).
   - Every `val` and `var` is read, and every `var` is assigned or passed as `mut`; assigning a binding does not read it. Parameters are exempt, since a signature is an interface its callers fix ([`strict-defaults`](../docs/design-review.md#strict-defaults)).
   - A value nobody uses is an error: an expression statement has no value, or is discarded on purpose with `_ = e` ([`strict-defaults`](../docs/design-review.md#strict-defaults)).
   - Assignment `x = e` and element assignment `a[i] = e` apply to a `var` or a `mut` parameter, and `x += e` means `x = x + e`, likewise for the other arithmetic and bit operators.
   - A block runs its statements in order. Its value is its last statement when that is an expression; a function with a result type must produce a value of that type on every path that does not leave it by `return` or a trap.
   - `if c { a } else { b }` evaluates `c`, then one branch, and is an expression whose type both branches share. Without `else`, `if` is a statement.
   - A branch of an `if` or an arm of a `match` that leaves has any type. A block leaves when one of its statements is `return`, `break` or `continue`, or is an expression statement, a discard, a binding or an assignment whose value leaves; a value leaves when it is `todo`, `unreachable`, or an `if` or a `match` whose every branch leaves; and an arm written as a value leaves when that value does. A loop's or a `guard`'s condition and the indexes of an assigned place do not count here. A branch whose value only holds an operand that leaves, as `x + todo("r")` does, still gives its operation's type, which the other branches share: `if c { x + todo("r") } else { true }` is an error.
   - An `if` or a `match` whose every branch leaves has any type and gives no value, as `todo` does: control never reaches past it, so the binding, the element, the argument or the operand it would give a value to never holds one. So does a repeat of a value that gives none, which evaluates its value once, however many copies it makes, none included; an array literal of at least one element, every one of which gives none, `[]` being a value; and a field, an element or a `.len` read of a value that gives none: each evaluates what it holds in order, and leaves where the first of them does. Its type tells this only for an array of at least one element: a repeat of no copies has the type of `[]`, an array of no element, which has a value, so where it leaves is told by its evaluation alone, wherever it stands.
   - `while c { body }` repeats `body` while `c` holds. `break` leaves the innermost loop, and `continue` starts its next iteration.
   - `guard c else { body }` continues when `c` holds. Its `body` must not reach its end: it leaves by `return`, `break`, `continue`, `todo` or `unreachable`. After a `guard`, `c` is a fact Tier 1 holds.
   - A statement reaches its end only when every operand it always evaluates does, the indexes of the place an assignment writes included: `_ = x + todo("r")` and `ys[todo("r")] = x` leave as `todo("r")` does, and so does a statement with an operand that is an `if` or a `match` whose every branch leaves. The right operand of `and` and `or`, the branch of an `if` without `else` and a loop's body may not run, so what they hold leaves nothing. This decides `E0210` and `E0211` only; the type of a branch follows the rule above.
   - `and` and `or` evaluate their right operand only when it decides the result; `not` negates.
   - `todo("reason")` has any type and traps when it runs (`surface-syntax.md`, item 7).
   - `unreachable("reason")` has any type and traps when it runs; it states a case its author knows cannot happen, and Tier 1 erases it where it proves the case impossible (`surface-syntax.md`, item 9).
   - `Implemented`: name resolution. A name is visible from its declaration to the end of its block, and an unknown name is an error whose fix suggests the closest visible name (`E0201`); a second declaration of a name in a function is an error whose fix renames it and its uses (`E0202`); `break` and `continue` stand inside a loop (`E0208`).

7. `Specified` **Functions and parameter modes** (`mutable-value-semantics.md`):
   - A function's parameters are read-only by default. A read-only parameter is a value the function cannot change.
   - A `mut` parameter receives a place, marked at the call site: `f(mut x)` or `f(mut a[i])`. Its value is copied in when the call starts and copied back on every return, so the caller's place holds the parameter's final value. The place has the parameter's type exactly, refinements aside, which Tier 1 proves at each copy, so the copy back never fails and the place can be passed by address ([`mut-argument-type`](../docs/design-review.md#mut-argument-type)).
   - Within one call, a `mut` argument's root binding may not appear in any other argument: `f(mut a[i], a[j])` and `f(mut a[i], mut a[j])` are errors, whatever `i` and `j` are.

12. `Specified` **Plain and owning types** ([`copy-and-drop`](../docs/design-review.md#copy-and-drop), [`value-copy-cost`](../docs/design-review.md#value-copy-cost)):
    - Every type is plain or owning, by its structure. An owning type holds a heap buffer: `String`, `List<T>`, and every array, struct, enum and `?T` that holds an owning type. Every other type is plain: integers, `bool`, views, and arrays, structs, enums and `?T` of plain types.
    - A plain value is copied, bit for bit, wherever it is bound, assigned, passed or returned, and `own` never makes its binding unusable.
    - An owning value is never copied implicitly. A place of owning type gives its value only where `own` is written or where its life ends anyway: `val b = own a` and `f(own a)` move it, `a.clone()` copies it at a cost the code shows, and `return a`, `raise a` (item 16) and a body's last expression `a` move a local binding or an `own` parameter, since nothing after them can read it. Anywhere else, as in `val b = a`, `b = a`, a field of a struct being built or an element of an array literal, it is an error whose fixes are `own a` and `a.clone()`. An owning value that no binding holds, such as a call's result, moves to where it lands.
    - A read-only argument of owning type is passed without a copy: the callee reads the caller's value, which the Law of Exclusivity keeps unchanged for the call (item 20). No later operand of the same expression may change it either: where a plain value would be kept as a copy, an owning one is an error (item 20).
    - An owning value is freed, every buffer it holds included, when the binding that holds it ends: at the end of its block, in the reverse order of declaration; on every exit from the block, by `return`, `break`, `continue`, `raise` or `!`; and when a value is assigned over it, after the new value is computed. A moved binding is not freed, since its value lives on elsewhere. An owning value that nothing holds, such as a call's result passed to a read-only parameter, is freed at the end of its statement.

An owning value nothing holds that one of them makes is freed when it has its value, before a branch, a round, the other operand or what consumes the arm's value runs; so a loop frees it in every round, and holds no more for running longer. The scrutinee of a `match`, an `if val` or a `guard val`, and the call of a `catch`, is no such part: an owning one that nothing holds is held to the end of the statement it stands in, as items 14 to 16 say. 14. `Specified` **Enums and `match`** ([`struct-enum-syntax`](../docs/design-review.md#struct-enum-syntax), [`match-patterns`](../docs/design-review.md#match-patterns)):
    - `enum Name { ... }` declares a nominal type whose value is one of its variants, written one per line (`grammar.md`, item 10). A variant holds nothing, as `A`, or a payload of named fields, as `B(field: T, ...)`.
    - A variant is always named with its enum: `Name.A`, and `Name.B(field: e, ...)`, built as a struct is (item 13).
    - `match e { pattern => arm ... }` evaluates `e` once and runs the first arm whose pattern matches it. An arm is an expression or a block. A `match` gives a value whose type its arms share, or stands as a statement, as `if` does.
    - A pattern is one of these, and none nests inside another:
      - a variant, `Name.A` or `Name.B(field: x, ...)`, which names every field of the payload in order and binds each to a name or to `_`;
      - an integer literal, with `-` before it or not, or `true` or `false`;

An arm that no value can reach, behind an earlier arm or outside the scrutinee's range, is an error.

A new value for the place is written as a transition, `state = match state { ... }`.

15. `Specified` **Optional values** ([`optional-semantics`](../docs/design-review.md#optional-semantics)):
    - `?T` holds `none` or a present value of `T`. It is a tagged type of its own: `??T` holds `none`, or a present `?T`, which may itself be `none`.
    - `none` takes its type from the place it lands in. Where no place gives one, as in `val x = none`, it is an error that asks for the type.
    - A value of `T` becomes a `?T` only where it lands in a place of that type, at the narrowing points of item 4: a binding's initializer, an assignment, an argument, a returned value, a field being built, an element of an array literal and an element store. Nowhere else does a `T` stand for a `?T`.
    - A present value is reached only by binding it to a new name: `guard val v = e else { ... }`, `if val v = e { ... } else { ... }`, or `match e { none => ... v => ... }`. `e == none` and `e != none` are comparisons and narrow nothing, since one name never has two types (item 6). The new name is a read-only projection, as a pattern's binding is (item 14).
    - `Specified` **`if val`**: `if val v = e { a } else { b }` evaluates `e` once; `e` has a type `?T`. When it holds a present value, `v` names that value, of type `T`, and `a` runs; otherwise `b` runs, where `v` is not visible. As an expression its branches share one type, as an `if`'s do (item 6); without `else` it is a statement. A value of `e` that no binding holds, such as a call's result, is freed at the end of its statement, as a `match`'s scrutinee is (item 12); `v` is visible only in `a`, which that statement holds. It has no trap of its own.
    - `Specified` **`guard val`**: `guard val v = e else { b }` evaluates `e` once; `e` has a type `?T`. When it holds `none`, `b` runs, and does not reach its end (item 6, `E0211`); otherwise `v` names the present value, of type `T`, from the statement after the `guard val` to the end of its block. A value of `e` that no binding holds, such as the result of `make()` in `guard val v = make()`, lives to the end of the block, past its own statement, unlike a `match`'s scrutinee, since `v` reads it until then; it is freed there with the block's bindings (item 12). It has no trap of its own.
    - `Specified`: the new name of `if val` and `guard val` is a read-only projection, so `e`'s place is frozen wherever the construct can read it, as a matched place is in every arm (item 14; [`match-arm-freeze`](../docs/design-review.md#match-arm-freeze)): in both branches of `if val v = e`, its `else` included, and in `guard val v = e`'s `else` block and from the `guard val` to the end of its block. `e`'s place is `e` itself where `e` is a place, a binding followed by fields and indexes (item 14), and where `e` is `x?.f`, or a chain of `?.`, the place `x` names: binding the value of `p?.name`, in `if val`, `guard val` or a `match`, freezes `p`, as a pattern's binding freezes its scrutinee's place, since the name reads the field in place (the `?.` claim below). So each of these is `E0232`: `cur = c.next` after `guard val c = cur`; `cur = reload()` in `guard val c = cur else { cur = reload()  continue }`; and `p = none` after `guard val n = p?.name`, which would free the `String` that `n` reads.
    - `Specified`: `E0232`'s fix after a `guard val` rewrites the block from the `guard val` onward, since a later assignment is still inside the frozen region, as item 14's transition form, the new value given by a `match` on the place: `cur = match cur { ... }`. As for a `match` statement (item 14), it is offered only where the statements from the `guard val` onward end by assigning the whole place or leave it as it is, read the new name nowhere after that assignment, and leave the place's indexes, literals or names, unchanged: `...; cur = c.next; c.v` takes none.
    - `e?.field` reads a field of a present struct, and gives `none` when `e` is `none`; for a field of type `U` its type is `?U`. It only reads: a write through `?.` is an error whose fix narrows with `guard val` first, so a write never silently does nothing.
    - `Specified` **`?.`**: `e?.f` evaluates `e` once; `e` has a type `?T` for a struct `T` whose field `f` has type `U`, and `e?.f` has type `?U`. When `e` holds `none` it gives `none`, and otherwise the present value's field `f`, as a read-only projection: nothing is copied. Read where it stands, as an operand of `==` or a read-only argument, it is a read of the field in place, whatever `U` is, so `p?.name == q?.name` compares two `String` fields. A name bound to its present value, by `if val`, `guard val` or a `match` arm, reads the field in place too, so the place `e` reads from is frozen while the name lives, as above. A value of an owning `?U` that lands in a place, as in `val n = p?.name`, is item 12's implicit copy, an error whose fix narrows `p` with `guard val` and then clones the field. It has no trap of its own.
16. `Specified` **The error union `T ! E`** ([`error-union-semantics`](../docs/design-review.md#error-union-semantics), [`error-conversion`](../docs/design-review.md#error-conversion)):
    - A function's result type may be `T ! E`, or `! E` for a function that gives no value, where `E` is an enum. `T ! E` is a result type only: no binding, field, parameter or type argument has it. In `?T ! E` the error is outermost.
    - `raise e`, where `e` has the function's error type, ends the function with that error. It is an expression of no value, as `todo` is. `mut` parameters are copied back on this exit as on every other (`mutable-value-semantics.md`, item 4), and `ensures` clauses hold at normal returns only.
    - `Specified`: `raise a` moves a local binding, an `own` parameter or the error a `catch` arm binds, as `return a` does (item 12), since nothing after it can read the binding (Norman, 2026-11-13). So `f() catch { e => raise e }` raises `f`'s owning error without a copy.
    - A call of a function that can fail is handled where it is written, by postfix `!` or by `catch`. A call handled by neither is an error, `_ = f()` included.
    - `f()!` gives `f`'s value, or ends the calling function with `f`'s error. It stands only in a function whose error type is `f`'s; another error type is converted with `catch`.
    - `f() catch { arm ... }` gives `f`'s value, or runs the arm that matches its error. The arms are patterns over the variants of `f`'s error type, exhaustive as `match`'s are, or one arm that binds the whole error to a name: `f() catch { e => raise AppError.Parse(cause: e) }`. Each arm gives a value of `f`'s value type, or leaves by `return`, `raise`, `break`, `continue`, `todo` or `unreachable`. The error an arm binds is that arm's: an owning one is freed at the arm's end unless it is moved.
    - `!` is a postfix operator, so `f(x)! + 1` adds to `f`'s value. `f()!= 3` is `f() != 3`, a comparison of a call left unhandled, which is an error; `f()! == 3` compares the value.
    - When `main` fails, the program ends with its error, printed as item 23 says, and with an exit status of its own, apart from a trap's.
    - Native code returns `T ! E` as `error-handling-abi.md` (item 2) says: a tag and a payload in two registers when the payload fits 8 bytes, the payload in a buffer the caller passes when it does not ([`error-return-spike`](../docs/design-review.md#error-return-spike)).
17. `Specified` **Views** ([`slice-ranges`](../docs/design-review.md#slice-ranges), [`read-only-views`](../docs/design-review.md#read-only-views), [`view-source-freeze`](../docs/design-review.md#view-source-freeze), [`view-provenance-sources`](../docs/design-review.md#view-provenance-sources)):
    - A view is a read-only window onto values held elsewhere: `[]T` onto a contiguous run of `T`, and `str` onto UTF-8 text (item 18). A view is plain: copying it copies the window, never the values.
    - A view is made only explicitly, from an array, a `List`, a `String` or another view: `xs[..]` views the whole, and `xs[a..b]` the elements from `a` up to but not including `b`. `a` and `b` may have any integer type. `0 <= a <= b <= xs.len` is checked at run time, and the check is erased where Tier 1 proves it; a range outside it traps. A range has no open end and no `..=`.
    - `v[i]` reads an element, its index checked as an array's is, and `v.len` is the window's length. Nothing writes through a view: an element store through one is an error. A `var` view, or a `mut` view parameter, can be given another window, which changes no element.
    - A view's sources are the owners and views it was made from, and a `var` view's are those of every value assigned to it. While a binding holds a view, or a struct or enum that holds one, its sources are frozen for the whole block that declares the binding: nothing assigns to them or to any part of them, passes them as `mut` or `own`, or calls what changes them. A view that no binding holds, such as the argument of `f(xs[..])`, freezes its sources for its statement, where a statement ends as item 12 has it for an owning value nothing holds: a condition, a clause, an arm and a branch each end as one, so `while n(xs[..]) > 0 { mut xs.pop() }` freezes `xs` for the condition and not for the body. A view of a value that no binding holds, such as a call's result, is an error.
    - A function that returns a view, or a value that holds one, takes it from its parameters, as its signature says (`regions-and-pools.md`, item 1): by default from every read-only parameter that is or holds a view, and with `from p, q` from the ones named. Only such parameters can be sources: a `from` that names a `mut` or `own` parameter, or an owner such as an array, a `List` or a `String`, is an error (`E0311`). A caller holds the result as a view of its arguments' sources.
    - A view that would outlive its sources, stored where it lasts longer than they do, is an error (`E0310`). Its fixes are an owned copy in M2 (`String.from`, `List.from`) and, as Engineering Guardrail #3 requires, an arena or a `Pool<T>` with `Handle<T>`, which come in M3.
    - `Specified` **Holding a view is a property of a type** ([`view-holder-types`](../docs/design-review.md#view-holder-types)): it is derived from the type's fields and type arguments, and never written by hand. `[]T` and `str` hold a view; a struct, an enum, an array, `?T` or `List<T>` holds one when any part of it does: a field, a field of a payload, an element or the present value. Integers, `bool` and `String` hold none. A view holder takes three rules of a view, and only these: provenance, in that its sources are the union of its parts' sources, it is returned only from the parameters its signature names, and storing it where it outlives its sources is `E0310`; the freeze, in that a binding that holds it freezes its sources as one that holds a view does; and the rule on type arguments below. Holding a view makes a type neither plain nor read-only: a `List<[]u8>` is owning, moved, cloned and freed as item 12 says, and its elements are stored as any `List`'s are.
    - `Specified`: `mn view --spec` prints the property on the declaration of each type that holds a view, and the property is part of `spec_hash` (`holographic-module.md`, item 3). So a change that makes a type hold a view, or stop holding one, reaches its dependents even where the type's own declaration reads the same, as when the type of one of its fields changes.
    - `Specified`: a view holder is never a type argument of `Pool<T>`, `Shared<T>`, `Local<T>` or `Channel<T>`, which come in later milestones, since a value of each may outlive the views it would hold. Such a type argument is an error whose fix copies the viewed data into an owned value (`String.from`, `List.from`): the fix `E0310` offers through a `Pool<T>` would be circular here. So when `E0310` reports a view holder that would outlive its sources, its `Handle<T>` path, as Engineering Guardrail #3 gives it, keeps the viewed data in a `Pool<T>` of owned values and a `Handle<T>` where the view was; it never means a `Pool` of the view holder itself.
    - `Specified`: from M4, which brings generics, a type parameter is assumed to hold a view unless it is bounded `T: ViewFree`, so that a generic container's rules are checked once, at its declaration.
    - `Specified`: iteration over an array or a view has one form, `for x in xs`, which the compiler lowers over a view of `xs`. No milestone brings `for` yet (`grammar.md`, item 8). A user's iterator is a view holder whose `next` takes it as `mut`.
18. `Specified` **Text** ([`str-text-model`](../docs/design-review.md#str-text-model)):
    - A `str` is always valid UTF-8, and its `.len` counts bytes. A string literal is a `str` of static storage, a source that nothing frees.
    - A `str` has no index. `s.bytes()` is a `[]u8` view of its bytes. `s[a..b]` is a `str` whose bounds must also fall on character boundaries: one that cuts a character traps, unless Tier 1 proves it does not.
    - `String` is UTF-8 text a value owns (item 12): `String.new()` is empty, `String.from(s)` copies a `str`, `mut t.push(s)` appends one, `t.len` counts bytes, `t[..]` and `t[a..b]` are views of it, and `t.clone()` copies it.
    - A byte literal `b'x'` is the `u8` of an ASCII character. String literals gain the escapes `\r`, `\0` and `\xNN` for `NN` up to `7F`, so that every literal is valid UTF-8 (`grammar.md`, item 9).
19. `Specified` **`List<T>`** ([`list-string-m2`](../docs/design-review.md#list-string-m2), [`sympathetic-defaults`](../docs/design-review.md#sympathetic-defaults)):
    - `List<T>` is a growable run of values of `T` that it owns, contiguous on the heap. Its operations are a closed set, and no others exist before M4's traits:
      - `List.new()`, an empty list whose element type comes from the place it lands in, as `none`'s does, and `List.from(v)`, a copy of a view `v` of plain elements;
      - `xs.len`; `xs[i]`, which reads an element, its index checked; and `xs[i] = e`, which stores one in a `var` or `mut` list;
      - `mut xs.push(e)`, which appends `e`, moving it as `own` does when `T` is owning; `mut xs.pop()`, which removes the last element and gives it as a `?T`, `none` when the list is empty; and `mut xs.swap(i, j)`, which exchanges two elements, each index checked;
      - `xs[..]` and `xs[a..b]`, which are views (item 17), and `xs.clone()`, a copy with each element cloned.
    - A push onto a full list doubles its capacity, to at least four elements, and moves its elements once; the cost report shows where this happens. An allocation that fails, or that asks for more bytes than an address holds, traps with a kind of its own.
20. `Specified` **Parameter modes, moves and exclusivity** ([`own-invalidation`](../docs/design-review.md#own-invalidation), [`exclusivity-projections`](../docs/design-review.md#exclusivity-projections)):
    - M2 has three parameter modes: read-only, `mut` and `own` (`mutable-value-semantics.md`). `in` comes with arenas in M3.
    - An `own` parameter receives a value the callee owns, to free or move on. The argument is marked, `f(own a)`, and is a whole local binding or an `own` parameter: nothing moves out of a field or an element, and a read-only or `mut` parameter never moves, since its caller still holds it.
    - A binding moved on any path is dead where the paths join, and reading it there is an error. Only assigning a `var` on every path brings it back. Where one branch moves a binding, every other branch moves it too or discards it with `_ = own a`, so no flag is kept at run time. A binding declared outside a loop and moved inside it is brought back before the loop's next round, or the loop leaves after the move.
    - Within one call, the root binding of a `mut` or `own` argument appears in no other argument: item 7's rule, for every projection. `f(mut s.a, mut s.b)`, `f(own a, a.len)` and `f(mut xs[i], xs[j])` are errors.
    - A call that changes its receiver is marked: `mut xs.push(v)`. The receiver counts as a `mut` argument, so `mut xs.push(xs[0])` is an error whose fix reads the element first. A call that only reads its receiver, such as `s.bytes()`, is not marked.
    - `Specified` **An owning place a later operand would change** ([`owning-operand-exclusivity`](../docs/design-review.md#owning-operand-exclusivity)): within one expression, a later operand may not change an owning place that an earlier operand read. This carries the rule above from the arguments of one call to calls nested in them: `two(xs, bump(mut xs))`, with `xs` a `List`, is an error where the module is checked. A plain value read there keeps the value it was evaluated to, as a copy (item 12); an owning value is never copied implicitly, so there is nothing to keep, and no copy is made. The fix binds a `.clone()` of the place first, at a cost the code shows, or moves the call that changes it into an earlier statement. The rule applies to every list of operands that item 25's rule of a value kept names: the receiver and the arguments of a call, the two operands of an operator, the fields of a struct or a variant built, the elements of an array literal, and the base of an element read against its index. So the two rules cover the same sites: a plain place is kept, and an owning place is an error. To change it is to pass it `mut`, to assign it, or to move it away: the later operand holds, at any depth, a `mut` or an `own` argument, or an assignment, whose place has that binding as its root. So `two(xs, eat(own xs))` is the same error: `eat` would free the list before `two` reads it. The error's code comes with `List<T>` and `String`.
    - `Implemented`: within one call, the root binding of a `mut` argument appears in no other argument, through fields and elements alike and inside an `if` that is an argument: `f(mut s.a, mut s.b)` and `f(mut s.a, s.b)` are errors (`E0207`).

24. `Specified` **The kernel and its elaborations** ([`elaboration-to-core`](../docs/design-review.md#elaboration-to-core)):
    - The rules of this file are of two kinds. The kernel is the smallest set of constructs with typing, evaluation and trap rules of their own. Every other construct is defined by an elaboration, a translation into the kernel, written below as a claim. A name below that begins with `$` is a fresh name the elaboration makes, which no name of the source can be.
    - `Specified`: the kernel of M2 is: literals and names; the arithmetic, bit, shift and comparison operators of item 4, `not`, and `==` and `!=` of item 22; `val`, `var`, `own`, assignment to a place and compound assignment; blocks and their statements, `if`, `while`, `break`, `continue` and `return`; calls, with read-only, `mut` and `own` arguments and on a receiver; `requires`, `ensures`, `invariant` and `decreases`, with `@checked` and `@prove`; `todo` and `unreachable`; array literals, element reads and `.len`; structs and variants built, fields read, and `match`; `none`, a value entering a `?T` at a narrowing point, and `?.` (item 15); `raise` and `catch`; views made from a range, `xs[a..b]`, and of a whole owner, `xs[..]`; and the operations of `str`, `String` and `List<T>` (items 18 and 19), `clone` among them.
    - `Specified`: a construct's own item defines its meaning. An elaboration is right only where it agrees with that item, and a disagreement between them is a fault in the elaboration, unless the item is shown to be wrong.
    - `Specified`: each elaboration is made once, in the front end, after type checking, so that a diagnostic speaks of the code its author wrote and the kernel program carries the types the check gave it. The lowering to MIR and Tier 1 see only the kernel. `mn dump --kernel` prints a program's elaboration in its canonical form ([`canonical-forms`](../docs/design-review.md#canonical-forms)).
    - `Specified`: the reference interpreter evaluates every construct of the source directly, by the rule of its own item, and is never given the elaboration. So it shares no code with the paths it checks (`CLAUDE.md`, invariant 2; [`reference-interpreter-crate`](../docs/design-review.md#reference-interpreter-crate)), and the comparison of the three execution paths checks each elaboration. A fix of a difference that comparison finds in an elaborated construct names, in its commit, which side was wrong: the elaboration, or the interpreter's direct rule.
    - `Specified`: the elaboration lives in a module of `mente-sema`, `elaborate`, and the kernel program is a type of its own, reached only through that module's entry point, which takes a `CheckedModule`. `CheckedModule`, which the interpreter reads, carries the source tree and no field or method that gives the kernel. The lowering and Tier 1 take the kernel from the entry point.
    - `Specified`: a test fails when `mente-interp` names the module, the kernel's type or any function that returns it, through a `use`, a path or a re-export, and when `mente-sema` re-exports any of them outside that module. Its evidence comes with the code. Whether the elaboration should rather live in a crate `mente-interp` does not depend on is weighed when that code is written, since Tier 1, which runs on the kernel, lives in `mente-sema` too.
    - `Specified`: Tier 1 speaks in the terms of the source, as Engineering Guardrail #1 asks, though it runs on the kernel. Every kernel node keeps the span of the source construct it came from; a fresh name is printed as the source expression it binds; a valuation names source bindings and the values of source expressions; and a `guard` prescription is written in source terms, so that it can be pasted where the obligation failed. Item 14's rule that a refinement a `match`'s or an `if`'s value fails offers no `guard` is judged on what the author wrote: it applies to a `match`, an `if` or an `if val` whose value fails, since a `guard` repeating any of them says nothing of it, and never to a `match` or an `if` an elaboration made of something else, such as the statements after a `guard val`, or `and` and `or`.
    - `Specified`: contract clauses, `requires`, `ensures`, `invariant` and `decreases`, are elaborated as any expression is, since Tier 1 sees only the kernel. A trap's text, and a diagnostic's, renders a clause from the source on every execution path (`ROADMAP.md` M2, what the review of pull request 120 left: trap messages print a clause as it is written).
    - `Specified`: a construct a later milestone brings is an elaboration, unless the entry that brings it says why none exists. `for x in xs` (item 17) is placed by the milestone that brings `for`.
    - `Specified` **Discarding**: `_ = e` is `{ val $d = e }`, and `_ = own a` is `{ val $d = own a }`: the value is bound to a fresh name nothing reads and freed where the block ends, inside its statement, as item 12 frees a value nothing holds. Item 6's rules on what may be discarded (`E0217`, `E0203`), and item 16's on a call that can fail, are checked on the source.
    - `Specified` **`guard`**: `guard c else { b }` is `if c { } else { b }`. Since `b` does not reach its end (`E0211`), only the path on which `c` holds continues after it, and Tier 1 holds `c` there (item 6).
    - `Specified` **Compound assignment and `xs[..]` are kernel constructs.** `p op= e` and `xs[..]` evaluate the path of their place once, each index checked in item 12's order before the next is evaluated, and `p op= e` checks it again where it stores (item 10). No kernel construct does that without an alias to the place, and an alias is unsafe here: a `mut` call in `e` that shrinks a `List` would leave it pointing past the list's end, and Tier 1 would have to track aliases, which mutable value semantics exists to avoid. Safety comes before a smaller kernel (Norman, 2026-11-13).
    - `Specified` **`and` and `or`**: `a and b` is `if a { b } else { false }`, and `a or b` is `if a { true } else { b }`, so the right operand runs only when it decides the result (item 6).
    - `Specified`: Tier 1 narrows a condition through an `if` whose value is a `bool`, and proves an obligation written with `and` or `or` through its elaboration, so that every condition and every obligation it proves today stays proven once they are elaborated: a refinement, and a contract clause such as `requires x > 0 and x < 10` at each call and an `ensures` at each return. The evidence this claim will need is a test that runs Tier 1 over the conformance suite and generated programs both ways, with `and` and `or` written and as their elaboration, and finds the same facts after each condition and the same obligations discharged.
    - `Specified`: `==` and `!=` on arrays, views, text, structs, enums and `?T` (item 22) stay in the kernel until M4's traits, and then become a library under the rule "library first" ([`feature-admission`](../docs/design-review.md#feature-admission)).
    - `Specified` **`if val`**: `if val v = e { a } else { b }` is a `match` on `e` whose `none` arm runs `b` and whose arm `v` runs `a`; without `else`, the `none` arm is an empty block. So `v` is a read-only projection of `e`, and `e`'s place is frozen in both branches, as item 15 says.
    - `Specified` **`guard val`**: `guard val v = e else { b }`, with the statements `R` that follow it to the end of its block, is a `match` on `e` whose `none` arm runs `b` and whose arm `v` runs `R`, the block's value being the `match`'s. So `v` is a read-only projection of `e`, and `e`'s place is frozen to the end of the block, as item 15 says.
    - `Specified` **`?.` is a kernel construct.** Its value is a read-only projection of an optional field, which no kernel construct gives. Patterns do not nest (item 14), so a `match` on `e` can bind only the present struct, `$v`, and the arm's value `$v.f` is then a copy of the field: item 12 rejects it for an owning field, which would reject `p?.name == q?.name` for a `String` field, a read item 15 accepts. Its rules are item 15's.
    - `Specified` **Postfix `!`**: `f(a)!` is `f(a) catch { $e => raise $e }`: the error `f` gives ends the calling function as its own, moved as item 16 lets `raise` move a `catch` arm's error. The translation is exact because `!` stands only where the two functions' error types are one (item 16, [`error-conversion`](../docs/design-review.md#error-conversion)); `catch` stays in the kernel.

25. `Specified` **The stack budget** ([`stack-budget`](../docs/design-review.md#stack-budget)):
    - A run has a stack budget of 1,048,576 bytes. This item fixes it for every program: no command sets another, and nothing a program writes does. The stack in use is the sum of the frames of the calls that have begun and not returned.
    - A function's frame is a number of bytes that follows from its declaration and its body by the sizes of item 21. It is the sum of 64 bytes for the call itself, of what each parameter counts, of 16 bytes for each `decreases` clause of the function, and of the most its clauses and its body hold at one moment, which the two claims below define. So every call counts at least its 64 bytes, and a recursion through frames that hold nothing ends.
    - A parameter counts what crosses the call (`mutable-value-semantics.md`, items 1 and 4; [`mut-argument-type`](../docs/design-review.md#mut-argument-type)): an integer or a `bool` parameter counts its type's size; an `own` parameter counts its type's size, since the callee then holds the value; any other read-only or `mut` parameter counts 8 bytes, an address, since the callee reads or changes its caller's value in place.       | `if`, `match`, `if val` | See below | The size of its value's type where it gives a value, and nothing where it stands as a statement |
      | A value narrowed where it lands in a place of another type (item 4), a returned value and a body's last expression among them: an integer into another integer type, an array whose elements are narrowed, a `T` or a projection that enters a place holding a `?T`. A refinement of the value's own type is no other type, and neither is the type a `match`'s scrutinee enters, which is its own. The argument of a read-only parameter of a type `?T` that is passed as an address or none is not narrowed either: it is passed where it lies (`mutable-value-semantics.md`, item 1) | The value | The size of the type it enters, beside the value it was, which is held until the narrowing is done |
      | `raise e` | `e` | Nothing: it leaves |
      | `todo("reason")`, `unreachable("reason")`, and any expression that gives no value | None; a reason is no value | Nothing |

    - `Specified` **What is held at once.** A frame counts the most its function holds at one moment, not the sum of all it ever holds, and one principle says for how long anything is held: a value is held until what consumes it is complete. An operand is held until the operator's value is made, and an argument until the call returns. The value of a branch or of an arm is held until the value of its `if`, `match` or `catch` is made, and so are a scrutinee and what a failing call returned. A block's bindings, and the value of its last expression, are held until the value made from the block's value is made. The equations below apply the principle to each production of `grammar.md` that gives a value or holds one; they decide, and a production without one is a fault of this item:

      ```text
      size(T)  the size of type T (item 21)
      v(e)     what the value of e holds, by the table
      m(e)     the most held while e is evaluated, the making of its value included
      o(e)     v(e) where e gives a value of an owning type that no binding holds; else 0.
               It is 0 for own a, which a binding held, and for the call of a catch or
               of a !, whose value or error moves into what the catch gives or into
               the name an arm binds
      l(e)     the owning values no binding holds that the evaluation of e left held,
               each to the end of its statement (item 12); an equation below for each form
      r(e)     what is held once e has its value, until what consumes it is complete:
               r(e) = v(e) + l(e)
      c(e)     the size of the type e enters, where it lands in a place of another type
               (the row of a value narrowed); 0 where it does not
      m'(e)    = max( m(e), r(e) + c(e) )        e is evaluated, then narrowed
      r'(e)    = c(e) + l(e) where c(e) > 0, else r(e)
      M(s)     the most held while a statement s, a block, an arm or a branch runs
      R(B)     what is held of a block, an arm or a branch once it has given its value,
               until the value made from that value is made

      A literal, none, own a, todo, unreachable:
        m(e) = v(e)        l(e) = 0
      ( e ) is e. A pattern holds nothing: its names are places.

      Operands e1 .. en and a value: an operator, not, a place read, a projection,
      a mut argument, a read of a value that is no place, .len, a view made:
        m(e) = max( r(e1) + .. + r(e[i-1]) + m(ei)       for each i,
                    r(e1) + .. + r(en) + v(e) )
        l(e) = l(e1) + o(e1) + .. + l(en) + o(en)

      A place read, a projection, .len or a view of a place, with a base kept, of
      size k (the rule of a value kept, below): the base is held while it is read
        m(e) = k + the equation above over its indexes
        r(e) = v(e) + l(e) + k   where its value is an address or a view, which then
                                 reads the base kept; v(e) + l(e) where it is an
                                 integer or a bool

      An array literal, a repeat, a struct or a variant built, whose operands land
      as they are evaluated: the same, with m' and r' for each operand.

      A call f(a1 .. an), the receiver first (item 7):
        m(e) = max( r(a1) + .. + r(a[i-1]) + m(ai)                         each evaluated,
                    r'(a1) + .. + r'(a[i-1]) + r(ai) + .. + r(an) + c(ai)   then each narrowed,
                    r'(a1) + .. + r'(an) + v(e) )                           then the call returns
        l(e) = l(a1) + o(a1) + .. + l(an) + o(an)

      if c { B1 } else { B2 }, as an expression or a statement, with B2 or without:
        m(e) = max( m(c), M(B1), M(B2), R(B1) + v(e), R(B2) + v(e) )
        l(e) = 0           the condition and each branch end as a statement does (item 12)
      match s { p => A ... }, over its arms A:
        m(e) = max( m(s), r(s) + M(A), r(s) + R(A) + v(e) )
        l(e) = l(s) + o(s)   the scrutinee is held to the end of its statement; each arm ends
      s catch { p => A ... }, over its arms A:
        m(e) = max( m(s), r(s) + v(e), r(s) + M(A), r(s) + R(A) + v(e) )
        l(e) = l(s) + o(s)
      raise e, as a statement or as an arm:
        m = m(e); it gives no value and leaves: v = 0, l = 0, M = m(e), R = 0

      The elaborations count as their translations (item 24); the translation's count
      is the definition, and what follows "so" is what it comes to:
        a and b                           is  if a { b } else { false }
                                          so  m(e) = max( m(a), m(b), 2 ), l(e) = 0
        a or b                            is  if a { true } else { b }, likewise
        guard c else { B }                is  if c { } else { B }
                                          so  M = max( m(c), M(B) )
        if val x = s { B1 } else { B2 }   is  match s { none => B2   x => B1 }
        { S  guard val x = s else { B }  T }
                                          is  { S  match s { none => B   x => { T } } }
        s!                                is  s catch { $e => raise $e }
                                          so  m(e) = max( m(s), r(s) + v(e), r(s) + 8 )
        _ = e                             is  { val $d = e }
                                          so  M = size(T) + m(e), T the type of e

      A block { s1 .. sn }, where b(i) is the sizes of the bindings s1 .. si declare:
        M(B) = max( b(i-1) + M(si) )    for each i
        R(B) = b(n) + v(e)              where sn is the expression e that gives its value,
                                        and 0 where the block gives none
      An arm or a branch that is an expression e:
        M = m(e), R = v(e)

      val x: T = e, var x: T = e      M = size(T) + m'(e)
      p = e                           M = max( I(j-1) + m(ij), I(q) + m'(e) )
      p op= e                         is p = p op e, the indexes of p evaluated once (item 6):
                                      M = max( I(j-1) + m(ij), I(q) + m'(x) )
                                      x the operator p op e, whose operands are the value read
                                      from p, of size(P), and e, and which then lands in p
                                      i1 .. iq the indexes of p, I(j) = r(i1) + .. + r(ij),
                                      P the type of p
      while c  clauses  { B }         M = d + max( m(c), m(g) for each clause g, M(B) )
                                      d = 16 for each decreases clause, and 1 more if it has any
      return e                        M = m'(e)
      return, break, continue         M = 0
      e                               M = m(e)

      frame(f) = 64 + what its parameters count + 16 for each decreases clause of f
               + max( m(g) for each requires and decreases clause g,
                      M(body) + max( m(g) for each ensures clause g ) )
      The value a body gives, written = e or as the last expression of its block, is
      narrowed as a returned value: m'(e) in place of m(e).
      ```

    - Beside the equations, in words, and with the count each gives. Where no type is given, a value is a `u64`:
      - **An expression.** Its operands are evaluated in the order of the table, each held while the next is evaluated, and its own value is made while all are held. So `n + 1` holds 24 bytes, and `g(h(a / 2), h(a / 3), h(a / 4))` holds 40: two results and the 24 of the third argument. With `a: u8` and `b: u32`, `a + b` holds 21, the sum being of no one type, and 24 where it is then narrowed into a `u64`.
      - **A call.** Its arguments are all evaluated, then each is narrowed in order, then the call returns (item 7). So `f(wide(), make())`, with `wide() -> [1000]u64` into a parameter of `[1000]u8` and `make() -> [1000]u8`, holds 10,000 bytes: both values and the 1,000 the first is narrowed into.
      - **A value kept.** An operand that is a place read, or a projection, of a plain type other than an integer type or `bool` holds its type's size, in place of 8 bytes, where a later operand of the same expression may change its root binding, since it keeps the value it was evaluated to (item 12). That holds for every list of operands: the receiver and the arguments of a call, the two operands of an operator such as `==` on arrays, the fields of a struct or a variant built, the elements of an array literal, and the base of an element read against its index, under a field path or not. A later operand may change a binding where it holds, at any depth, a `mut` argument or an assignment whose place has that binding as its root; an `own` argument changes no plain value (item 12), and for an owning place it is one more way, which item 20 refuses. The rule reaches a base inside a read: where an index may change the root of the base it indexes, the base is kept, in a place read, in a projection, and in a `.len` or a view of a place alike, and it is held for as long as an address or a view read through it is. So in `use(Pair(a: xs, b: pick(mut xs, make())))`, with `xs` of 1,000 bytes and `make()` of 4,000, the field `a` holds 1,000 bytes while `b` is evaluated; `xs[bump(mut xs)]`, with `xs: [1000]u64` and `bump` giving a `usize`, holds 8,016; and in `use2(p?.big, wipe(mut p, wide()))`, with `big: [1000]u8` and `wide() -> [1000]u64`, the first argument holds the 1,001 bytes of its `?[1000]u8` while `wipe` runs, and the call 9,017. With `ps: [4]?Outer`, of 4,004 bytes, `use(ps[bump(mut ps)]?.a?.big)` holds 4,020: the base kept, and the 16 its index holds or the address and the call's value. With `vs: [1000][]u8`, of 16,000 bytes, `vs[bump(mut vs)].len` holds 16,016. A view is no such operand: it reads its owner in place, and item 17 freezes the owner, so `f(xs[..], g(mut xs))` is an error. And a place of an owning type is never kept: nothing copies it implicitly (item 12), so a later operand that may change it is an error (item 20), and there is nothing to count.
      - **An owning value no binding holds.** A value of an owning type that an expression gives and no binding holds is held to the end of its statement, where item 12 frees it or from where it has moved on, and not only until the expression it is an operand of has its value. So with `make() -> [100]String`, of 2,400 bytes, `total(make()) + total(make())` holds 4,824: both arrays, both results and their sum. A condition, an operand of `and` or `or`, an arm and a branch each end as a statement does (item 12), so nothing lingers out of one: `total(make()) > 0 and total(make()) > 1` holds 2,417, one array at a time; `x and ok(make())` holds 2,401; and `pair(match k { 0 => total(make())  _ => 0 }, wide())`, with `k: u8` and `wide() -> [1000]u8`, holds 2,409, the array being gone when `wide()` is called. A scrutinee is no such part: an owning one no binding holds is held to the end of its statement. The call of a `catch` or of a `!` leaves nothing behind it, since its value or its error moves on: with `f() -> String ! E` and `g` alike, `E` of one byte, `len(f()!) + len(g()!)` holds 89.
      - **`if`, `and`, `or`, `guard`.** The condition is evaluated, and ends. Then one branch runs, so of the branches only the one that holds the most counts. The value of an `if` is made while the value of the branch that gave it is held, and with it the bindings of that branch's block: `if c { m1() } else { m2() }` of `[1000]u8` holds 2,000 bytes, and `if c { var t = xs  fill(mut t)  t } else { xs }`, of the same type, holds 2,008: `t`, the read of it, and the value made from it. `a and b`, of two names, holds 2. With `xs: ?[1000]u8`, `if xs == none { 1 } else { 0 }` holds 16: the comparison holds 9, `none` nothing, and each branch's value stands beside the `if`'s.
      - **`match`, `if val`, `guard val`.** The scrutinee is evaluated and held while an arm runs and while the value is made, since a pattern's names read it in place (items 14 and 15); those names are places. Of the arms only the one that holds the most counts. So with `enum Msg { Empty(pad: u8), Big(data: [1000]u8) }`, `match get() { Msg.Empty(pad: _) => m0   Msg.Big(data: d) => d }` holds 2,009: the scrutinee's 1,001, the read of `d`, and the value. A scrutinee enters its own type, so with `a: u8` and `b: u32`, `match a + b { 0 => 1  _ => 2 }` holds 32: the sum's 16, an arm's 8 and the value's 8. `if val` and `guard val` count as the `match` each translates to, and that count is the definition: `fn g() -> [1000]u8 { guard val v = find() else { unreachable("x") }  v }`, with `find() -> ?[1000]u8`, has a frame of 2,073, the rest of its block being an arm whose value is made while the scrutinee is held.
      - **`catch`, `!`.** What the call holds is held while an arm runs and while the value is made, and an arm's value is held beside the `catch`'s. So `f()!` with `f() -> u64 ! E`, `E` of one byte, holds 25 bytes: the call's 17, and the 8 of its value or of the error an arm reads. And `f() catch { E.Bad => big() }`, with a value of `[1000]u8`, holds 3,009.
      - **A projection.** A place read through `?.` is an address, or none, where it is read in place, however long the chain: with `struct Outer { a: Inner }` and `struct Inner { big: [1000]u8 }`, `fn g(p: ?Outer) -> u64 { if val x = p?.a?.big { use(x) } else { 0 } }` has a frame of 96, and `use(p?.big)` holds 16, the address and the call's value, since a read-only argument of a type `?T` over 16 bytes is passed as an address or none (`mutable-value-semantics.md`, item 1), which is how item 15 has it read in place. An argument that is a `T` crosses in the same way: `use(xs)`, with `xs: [1000]u8`, into the same parameter holds 16 too. Where it lands in a place that holds a `?U`, the `?U` is built: `val q: ?[1000]u8 = p?.big` holds 2,010, the binding's 1,001, the address, and the 1,001 it is built into.
      - **`.len` and a view.** The indexes of the place they read are their operands: with `rows: [4][8]u8` and `wide() -> [1000]u64`, `rows[pick(wide())].len` holds 8,008.
      - **A block.** Its statements run in order. A `val` or a `var` holds the size of its type from the start of its own statement, while its initializer is evaluated, to the end of its block; whatever else a statement holds ends with the statement. So the count bounds a lowering that builds the value and then copies it into the binding, and one that builds it in place holds less: `val a = n + 1` holds 32 bytes; `val a: u64[0..10] = n` holds 16, a refinement being no other type; and `val a: [4]u64 = make()`, with `make() -> [4]u8`, holds 68, the binding's 32, the call's 4 and the 32 it is narrowed into. `_ = e` is `{ val $d = e }`: it holds a binding of `e`'s type and `e`, for its statement.
      - **A loop.** The condition, the clauses and the body of a `while` are held one after another, and the body once, however many rounds run: of these only the one that holds the most counts. A loop with `decreases` clauses also holds, for as long as it runs, 16 bytes for each clause, its measure of the round before, an exact integer, and 1 byte for the loop, whether a round has run, whatever the number of its clauses.
      - **An assignment.** The operands of `p = e` are the indexes of `p`, then `e`. A compound assignment `p op= e` is `p = p op e` with the indexes of `p` evaluated once (items 6 and 10): its operands are those indexes, then the value read from `p`, then `e`; the operator's value is made while they are held, and lands in `p`. So `x += f(x)`, with `f(u64) -> u64`, holds 24 bytes; `xs[i] += f(mut ys)`, with `xs` of `u32` elements, `i: usize` and `f` giving a `u32`, holds 24: the index, the value read, the argument and the call's value; and `x += e`, with `x: u8` and `e: u32`, holds 21, as `x = x + e` does, the sum being of no one type before it lands.
      - **`return`, `raise`.** The operand is evaluated, narrowed where the result's type is another, and held until the call returns.
      - **Clauses.** The expressions of a clause are held as any expressions are, in the frame of the function that declares it. A `requires` clause and the function's `decreases` clauses are evaluated on entry, before the body holds anything. An `ensures` clause is evaluated at a return, which may come where the body holds its most, so the `ensures` clause that holds the most is added to the most the body holds. The 16 bytes of each `decreases` clause of the function are its measure on entry, an exact integer, kept for the whole call.
    - So `fn down(n: u32) -> u32 { if n == 0 { return 0 }  down(n - 1) }` has a frame of 80 bytes: the call's 64, 4 for `n`, and 12 for its last statement, which holds `n`, `1` and `n - 1` together; its condition holds 9. `fn fact(n: u64) -> u64 { if n == 0 { return 1 }  n * fact(n - 1) }` has one of 104: 64, 8, and 32 while `n`, and then `n`, `1` and `n - 1`, are held. `fn mix(a: u8, b: u32) -> u64 { a + b }` has one of 93: 64, 5, and 24. And `fn f() -> u64 { todo("r") }` has one of 64.
    - No value is held nowhere. An argument that is no place, as in `f([1, 2, 3])` and `f(make())`, is a value its caller holds while the call is made; an argument converted on the way in is held by the row of a value narrowed; an operand that a later one may change by the rule of a value kept; and a `mut` projection gathered into a temporary by the row of a `mut` argument. A large value counts in the frame of the function that binds or builds it, and 16 bytes in each frame it is then passed through, read-only or `mut`: 8 for the parameter, and 8 for the read that passes it on.
    - What a call needs is what it holds at once, so branches that never run together are not added up: a `match` of fifty arms counts its largest arm, and a function of two hundred statements its largest statement and its bindings. A sum of all a body ever holds is simpler to state, and counts such a function at a hundred times what it holds at once, or more; and a sum of what is kept in memory would make a rule of the language out of what one lowering does with its slots (section 2).
    - `Specified`: the checker computes each function's frame once, as one number for each function, and the reference interpreter, MIR and native code read that number, as they read a layout (item 21). No execution path runs an elaboration to have it: the reference interpreter, which is never given the kernel (item 24), reads the number. So the three execution paths count alike and trap at the same call, and a test of the checker's count pins the rule itself.
    - `Specified`: an instrument holds the equations to the lowering, value by value. The checker gives every value the equations count a name of its own, the expression or the binding it is, with what it holds. The lowering names, for each slot it makes, the value the slot holds. For every function of the conformance suite and of the generated programs, a slot that names no value fails the test, and so does a slot larger than what its value holds. So a value the equations miss, or one they count too small, fails a test in CI, whatever else the function holds. A miss would not break the bound on native code's stack, which the measured ratio gives (`mir-and-codegen.md`, item 5): it would make the frame a wrong account of what a function holds, and the ratio larger than it need be. An equation for a construct not yet implemented is confirmed so when the construct is first lowered, and one the lowering cannot honour is changed here first.
    - `Specified`: once MIR says where a slot ends (`mir-and-codegen.md`, item 5), the instrument holds more: for the same programs, the slot bytes alive at any point never exceed the most the function holds.
    - Only a call of a function a module declares has a frame.
    - A call is counted once its arguments are evaluated, left to right (item 10), and before any is narrowed into its parameter's type (item 7). Where the stack in use and the callee's frame together exceed the budget, the call traps, and nothing of the callee runs; a call that fills the budget exactly runs. The frame is in use from there: while the arguments are narrowed, while the parameters' refinements, `requires` and `decreases` are checked, while the body runs, and while `ensures` is checked. Its bytes are given back when the call returns, by `return`, at the end of its body or by `raise` (item 16).
    - So a call inside an argument has returned, and given its frame back, before the call it is an argument of is counted.
    - A clause is evaluated where it is written, on every execution path, whatever was proven of it: a proof removes the clause's check, never an evaluation that can trap, as the lowering already has it (`mir-and-codegen.md`, item 2). So a call in a clause is a call as any other. It counts, in the scope that evaluates the clause, one in a callee's `requires` on top of the callee's frame; and no trap depends on what a prover proved. Erasure to no instruction is then for a clause that cannot trap (`ghost-contracts-and-totality.md`, item 2).
    - This order settles a case the two interpreters decide differently today. A call that would both run out of stack and narrow an argument out of its parameter's type traps as running out of stack, as the reference interpreter has it. MIR narrows the arguments and checks the callee's refinements, `requires` and `decreases` first, and so reports the narrowing.
    - Running out of stack is the trap of kind `stack-overflow`, whose text is `the call stack ran out`, at the call (item 9).
    - The run's first call, of `main` (item 10) or of the function `mn run --call` names, is counted as any call is, against a stack with nothing in use, and its frame stays in use for the whole run. The values a run is given from outside, and its result, are the run's own and count nothing.
    - Left open, each to the entry or the milestone that decides it. The routines that free, clone, compare and print a value descend with data that may nest without end, such as `struct Node { kids: List<Node> }`, in no declared call: what bounds them is decided with `List<T>`, before it is implemented ([`recursive-data-descent`](../docs/design-review.md#recursive-data-descent)). What `@max_stack(n)` promises of the machine's own stack, and what a call in `@branchless` code does, whose check is a branch, are decided before M5 implements them ([`max-stack-unit`](../docs/design-review.md#max-stack-unit)). A `dyn` call has no one callee to count, and a call of an `extern` function runs code that counts nothing: M4, which brings both, says what each counts; until then a program calls only functions with bodies (`E0224`). And a program has one stack until M7 brings tasks, each with a budget of its own (`structured-concurrency.md`).
    - `Specified`: a function whose frame is larger than the budget is an error where it is declared, since every call of it traps, as a narrowing that always traps is an error (item 8). Its fix names the largest parts of the frame, and only what the compiler's milestone has to hold them elsewhere, as `E0109` names a milestone: a smaller value, a value its caller passes in, and a `List<T>` (item 19), which holds its elements on the heap, once the milestone has it. The error's code comes with its implementation, beside a program that fails and its near miss, a frame of exactly the budget.
    - `Specified`: the cost report gives each function's frame, with what holds the most and the bytes of each part, and says of each call whether it is checked when it runs, and of each clause whether it stays evaluated ([`cost-report`](../docs/design-review.md#cost-report)). `@max_stack(bytes)` bounds a call graph in the same bytes; it erases checks where its bound fits and moves no trap (`hardware-contracts.md`, item 1). What native code does at a call, how large its real stack is, and the ceiling the compiler keeps on its machine frames, are in `mir-and-codegen.md` (item 5).

      - frames that hold nothing: `fn spin() { spin() }`, of 64 bytes, has 16,384 calls open and traps at its 16,385th; called from a `main` that holds nothing, it traps at its 16,384th;
      - a frame that does not divide the budget: `down`, above, of 80 bytes, has 13,107 calls open and traps at the 13,108th; `fact`, of 104, has 10,082 and traps at the 10,083rd;
      - a recursion that fills the budget exactly, and one call more: a function of 128 bytes, the call's 64, a `u64` parameter, four `u64` bindings and the 24 bytes its last statement holds, has 8,192 calls open and traps at the 8,193rd;
      - a function whose frame is the whole budget, which runs as the first call and traps at any call it makes, and the same with one byte more, the error above;
      - `main`'s own frame: a `main` whose frame is 600,000 bytes traps at its call of a function whose frame is 600,000, though each alone fits;
      - mutual recursion through frames of 80 and 96 bytes, begun in the smaller: 11,915 calls are open, and the 11,916th traps;
      - what is not added up: the branches of an `if`, two statements one after the other, the bindings of two blocks that follow one another, and the rounds of a loop;
      - what is: the arguments of one call, the operands of one operator, a binding beside its initializer, a scrutinee beside its arm and beside the value made from it, a branch's value and its block's bindings beside the `if`'s value, an arm's value beside the `catch`'s, and two owning values no binding holds in one statement;
      - what does not linger: an owning value made in a condition, in an operand of `and`, in an arm or in a branch, each gone before what follows it runs, the three examples above;
      - a value kept in each list of operands: `two(xs, bump(mut xs))`, a struct's field before a later field's `mut` call, an array literal's element, the left operand of `==` on arrays, and `xs[bump(mut xs)]`; and a base kept in a projection and under `.len`, the two examples above;
      - a call's arguments narrowed after all are evaluated, `f(wide(), make())` above; an integer of no one type, `mix` above, and as a scrutinee; a projection read in place through a chain, as a read-only argument and beside `none`, kept against a later operand, and built where it lands in a binding; the index of a place whose `.len` is read; a `T` and a projection passed into one read-only parameter of a type `?T`, with one count; and a compound assignment of two integer types beside the assignment it is;
      - each elaboration beside its translation, with one count: `guard val` and the `match` it is, above, `if val`, `!` and `catch`, `and` and `if`, `_ = e` and a binding;
      - a call inside an argument: `f(g(x))` runs where `g`'s frame and `f`'s each fit what is left and the two together do not;
      - a call at which the stack runs out and an argument does not fit its parameter's type: `stack-overflow`, not a narrowing;
      - a large array and a large struct passed down a recursion, read-only and `mut`, which count 16 bytes a call, beside the same recursion binding one in each frame, which counts its size: `walk(xs: [1000]u8, n: u32)`, which passes `xs` on, has a frame of 96 bytes against `down`'s 80;
      - an argument that is no place, `sum(make())` and `sum([1, 2, 3])`, held in the caller's frame, and an array argument whose elements are narrowed into its parameter's element type, held there too;
      - a call inside a callee's `requires` clause, which runs on top of the callee's frame, in a `@checked` function and in a `@prove` one;
      - calls made one after another in a loop, which do not add up.

## 2. Decision rationale and rejected alternatives

| Alternative considered | Reason for rejection |
| :--- | :--- |
| **Explicit conversions between integer types (Rust's `as`)** | Under exact arithmetic, `val x: u8 = a + b` is already checked at the binding, so `val x: u8 = y` for a `u32` `y` is the same narrowing. A cast would mark one case and not the other, and Rust's `as`, which truncates silently, is a bug agents write often. With no casts, nothing truncates silently: a plain type is checked at run time and a refined type is proven. |
| **Widening an unannotated binding to hold its expression's static range (`u8 + u8` as `u16`)** | It never traps at the binding, but the binding's type would change with the way the expression is written, which neither a reader nor an agent can predict. When the operands share a type, keeping it matches what agents expect from other languages; when they differ, no type is obviously right, so the programmer chooses. |
| **Defaulting every unannotated integer binding to `i64`** | Simple, but arithmetic on `u8` values would yield `i64` bindings, against what the code says. `i64` is kept only for expressions of literals alone. |
| **Shadowing, as in Rust (`let x = x + 1`)** | Refinement bounds name bindings (`usize[0..n]`). With a second `n` in scope, neither a reader nor an agent can tell at a glance which `n` a bound means. One name, one binding, at the cost of a new name after a transformation. |
| **Leaving `break` and `continue` to a later milestone** | Agents reach for them in almost every loop, and the first agent benchmark, at the end of M1, would otherwise score how well they work around their absence. They add no type rule, and Tier 1 counts a `break` as one more exit of its loop. |
| **Flooring division, as in Python** | Hardware, C, Rust and the languages agents know best truncate toward zero; a flooring function can be added beside `/` without changing what `/` means. |
| **Exclusivity by index (allowing `f(mut a[i], a[j])` when `i != j` is proven)** | It would make the Law of Exclusivity depend on Tier 1 proving a disequality, which octagons cannot hold in general. M1 takes the simple rule by root binding; a relaxation can come later without breaking programs that M1 accepts. |
| **A small-step semantics written as inference rules** | The rules here are prose, one claim each, so the tools hold each one to its evidence as it is implemented. A mechanised model is not built in stage 1 ([`mechanised-model`](../docs/design-review.md#mechanised-model)). |
| **Assignment of an owning value as an implicit move (Rust), or copy-on-write (Swift)** | A move at `val b = a` leaves `a` dead where nothing marks it, while `own` is written at every call that moves. Copy-on-write puts the cost of a copy at a later write, after a count is checked at run time, where neither a reader nor the cost report can place it ([`value-copy-cost`](../docs/design-review.md#value-copy-cost)). A `return` or a `raise` moves without a mark only because nothing after it can read the binding. |
| **Field defaults, and fields in any order at construction** | A default builds part of a value where the reader of the construction does not see it, and `= []` would allocate unseen. One order, the declaration's, makes every construction of a type read alike and evaluate in field order. Both can be added later without breaking a program. |
| **Freeing an owning value at its last use** | The end of its block is a point a reader sees, as a view's frozen sources end there too ([`view-source-freeze`](../docs/design-review.md#view-source-freeze)); a last use moves when the code changes. |
| **Narrowing a `?T` binding after `if x != none` (Kotlin, TypeScript)** | One name would have two types in two regions of its block, against one name, one binding (item 6). `guard val v = x` gives the present value a name of its own. |
| **A `some(v)` constructor and pattern** | A `T` lands in a `?T` place as an integer lands in a narrower type, and `match` binds the present value by name; a constructor would be a second spelling of the same value. |
| **`List<i64>.new()`, or a list literal `[]`, to start a list** | The element type is already written where the list lands, as `none`'s is. `[]` would allocate where it reads like an array, and is the array literal's. |
| **`-> void ! E` or a unit type for a function that fails without a value** | M2 has no unit type, and a type that holds nothing would be written only here. `-> ! E` says the function gives nothing but may fail. |
| **A marker written by hand on a type that holds a view (`~Escapable` in Swift, `ref struct` in C#), or provenance named per field** | A marker states what the compiler can derive from the fields, and can be forgotten; provenance named per field is a lifetime under another spelling (axiom 3). Derived, printed by `mn view --spec` and part of `spec_hash`, the property is on the page without being written ([`view-holder-types`](../docs/design-review.md#view-holder-types)). |
| **Every construct a primitive** | Each primitive is implemented on three execution paths, reasoned about in Tier 1, produced by the program generator and taught on the card, and it meets every other primitive; with nothing deciding, every construct becomes one and the calculus drifts. An elaboration is written once and checked by the three-path comparison ([`elaboration-to-core`](../docs/design-review.md#elaboration-to-core)). |
| **A kernel-only alias to a place, `place $p = grid[i][g()]`, so that compound assignment and `xs[..]` elaborate** | An alias outlives the evaluation of its path: a `mut` call in the right operand that shrinks a `List` would leave it pointing past the end, and Tier 1 would have to track aliases, which mutable value semantics exists to avoid. Safety comes before a smaller kernel, so both stay kernel constructs (Norman, 2026-11-13). |
| **Elaborating before type checking, or giving the reference interpreter the elaboration** | Before type checking, an error would speak of code its author did not write. An interpreter that ran the elaboration would share it with the paths it checks, so a wrong elaboration would pass the comparison. Elaborations users define are macros, which Mente does not have. |
| **Forbidding views in structs** | Parsers and tokenizers hold views of their input; without view fields they copy it or keep indices, the cost or the bugs views exist to remove. |
| **A stack limit of each execution path's own: a count of calls in the interpreters, and a handler on the guard page in native code** | The paths would trap at different calls near the limit, so one program would end in two ways, against one meaning for each construct. A handler would also be the runtime's least tested code, run on a stack that has just run out ([`stack-budget`](../docs/design-review.md#stack-budget)). |
| **A stack budget counted in calls** | A frame that binds a 64 KiB array would count as one that holds nothing, so no number of calls fits a real stack: native code would need a second limit in bytes, and the two could disagree. Bytes follow from the layouts a reader already sees (item 21), and `@max_stack(bytes)` composes in them. |
| **A stack budget counted in the machine's own frames** | They differ by target, by the compiler's version and by what its register allocator spills, so one program would trap at one depth on x86-64 and at another on AArch64, and the interpreters have no machine frame to count. |
| **A stack budget a command or a program sets** | One source would trap or not by how it was started, and the three paths could be run with three budgets. A program that needs more holds its data in a `List<T>`, whose elements live on the heap. |
| **Every parameter counted at its type's size** | It follows the copy that passing a value means (item 3), in one rule for every mode. But a recursion that passes an array down, read-only or `mut`, would count the array in every frame, though the callee works in its caller's place (`mutable-value-semantics.md`, items 1 and 4; [`mut-argument-type`](../docs/design-review.md#mut-argument-type)): a quicksort `sort(mut xs: [1024]i64, lo: usize, hi: usize)` would count 8,272 bytes a call and trap at its 127th. |
| **A frame that sums every value its body ever holds** | It needs no order of evaluation, and it grows with the code as a machine frame does under Cranelift, so native code's ratio would stay under 8 by construction and no function would be past the compiler's reach. But branches that never run together are added up. Measured on 2026-11-14: a recursive `match` of fifty arms of about twenty expressions sums to 15,745 bytes, against a machine frame of 1,696 and against 160 held at once, and would trap at a depth of 66; a recursive function of two hundred statements sums to 21,001 bytes against 128, and would trap at 49 ([`stack-budget`](../docs/design-review.md#stack-budget)). |
| **A frame that sums only what is kept in memory: its bindings, and its values other than integers and `bool`s** | It is the nearest to what the present lowering gives slots to, and is added up by eye. But it makes that lowering a rule of the language: the fifty-arm `match` sums to 2,080 bytes and would trap at 504 for good, also once a backend merges its slots; 256 levels of nesting through a function of two hundred arms would count 2 MiB; and a 128-bit integer no binding holds, which native code keeps in memory, would need a row of its own. It gives no ceiling on the ratio either: a function of 3,200 statements that each call stands at 146. |
| **A `@prove` clause evaluated on no path, its fate read from the signature** | Whether a clause's call runs would not depend on a prover either, and erasure would be whole. But the interpreters would stop catching a false trusted clause when a program runs ([`interpreter-checks-contracts`](../docs/design-review.md#interpreter-checks-contracts)). |
| **A clause whose evaluation counts nothing** | Native code still runs a `@checked` clause's calls on its real stack, so a clause could call only functions that declare `@max_stack`, which rejects programs that check today. |
| **Leaving native code's stack to `@max_stack` in M5** | Native code would crash until then, on programs the other two paths end with a trap. |
