# From-Scratch 64-Byte `SoA` Mente IR (`MIR`) and Multi-Backend Codegen

**Governs:** `compiler/mente-mir`, `compiler/mente-codegen`

## 1. Specification

1. `Implemented` **Index-addressed structure-of-arrays region** (`MirRegionSoA`, `compiler/mente-mir/src/lib.rs`):
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_nodes_are_rows_addressed_by_index" min="1" reason="Each node is one row of the parallel arrays, addressed by its NodeId" -->
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_interpreter_compares_and_selects" min="1" reason="The interpreter's comparisons, select and jump" -->
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_branchless_integrate_cell_mir_and_mutation_prover" min="1" reason="The interpreter evaluates a region over its arrays" -->
   - Every `MIR` instruction node is addressed by a 32-bit index handle (`NodeId(pub u32)`, `4` bytes) rather than a 64-bit heap pointer (`8` bytes).
   - `MirRegionSoA` stores one straight-line region in parallel vectors: `opcodes: Vec<MirOp>`, `types: Vec<MirType>` (`I64`, `Q16_16`, `Bool`), `inputs: Vec<[NodeId; 3]>`, `lattices: Vec<ValueLattice>` (an `i128` interval and an alignment per node), `lines: Vec<u32>`, plus `is_branchless_guaranteed: bool` and `ret_node`.
   - `MirOp` today: `Param`, `Const`, `Add`, `Sub`, `AddSatQ16`, `SubSatQ16`, `Shr`, `CmpGe`, `CmpLt`, `CmpEq`, `SelectBranchless`, `BranchCondJump`. There are no loads, stores, calls, loops or nested regions. The region serves the demo of `mn test --mutate`; functions lowered from source use the MIR of the next item.
   - `#[repr(align(64))]` on `MirRegionSoA` aligns the struct header only; the node arrays are ordinary heap `Vec`s.
   - `Specified`: packing nodes into 64-byte cache-line buckets.
2. **MIR as an SSA control-flow graph** (`compiler/mente-mir/src/cfg.rs`, [`mir-control-flow`](../docs/design-review.md#mir-control-flow)):
   - A function is a list of blocks, block 0 its entry, each with parameters, instructions and one terminator: a jump or a branch carrying the target's arguments, a return, or a trap. Its values, instruction results and block parameters alike, are rows of parallel arrays addressed by `NodeId`: operation, type, operands (a range of one shared pool) and source line and column.
   - Types are the integer types by width and signedness, `bool`, and addresses. Arrays live in memory, a stack slot or an address a caller passes, read and written by `load` and `store`; a `mut` parameter is an address too, so a call changes its argument in place.
   - Every value fits its type. An exact operation's operands and result share a type wide enough for its static range (`core-calculus.md` item 4), so it never overflows; a checked one, on `i128` or `u128`, computes its exact result from operands that may keep their own types, an `i32` beside a `u128`, and traps when that result leaves its type. Each run-time check is an instruction of its own, `check`, so a pass can erase one Tier 1 proved, and each trap site carries the message the reference interpreter prints for it.
   - `Implemented`: the MIR, a builder, a verifier of operands, types and jump arguments, and an interpreter that runs a function over byte-addressed memory, keeps its call frames on a stack of its own, stops at a depth and a step limit, and reports a trap in the reference interpreter's words; an exact operation that leaves its type is reported as broken MIR, a lowering bug.

     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_checks_trap_with_the_interpreters_message" min="1" reason="A check and a trap report what the reference interpreter prints" -->
     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_a_checked_operation_takes_operands_of_their_own_types" min="1" reason="A checked operation computes its exact result from operands of their own types" -->
     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_checked_arithmetic_traps_where_exact_arithmetic_is_a_lowering_bug" min="1" reason="A checked operation traps; an exact one that overflows is broken MIR" -->
     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_arithmetic_and_bits_follow_the_core_calculus" min="1" reason="Division, remainder, bits and shifts follow core-calculus.md" -->
     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_memory_holds_arrays_and_mut_parameters" min="1" reason="Slots, elements, loads, stores, copies and mut addresses" -->

     <!-- @assert-count target="compiler/mente-mir/src/cfg.rs" symbol="fn test_the_verifier_rejects_malformed_functions" min="1" reason="The verifier rejects malformed functions" -->
   - `Implemented`: `mente-codegen` lowers a checked module into this MIR, following the reference interpreter step for step: each operation in a machine type wide enough for its static range, a value narrowed and checked against its refinement where it lands, a call's arguments narrowed and its callee's refinements, `requires` and `decreases` measure checked by the caller, where those traps are located, `ensures` at each return, loop invariants and measures, and every trap the interpreter raises, in its words. Each function also gets an entry, which checks arguments from outside the program as a call does. A call whose argument does not have its parameter's shape, an integer, a `bool`, or an array of its length, is no call of the function, and is refused before anything runs, in the same words on the reference interpreter, through MIR and as native code. Every argument is first narrowed into its parameter's type, in order and element by element, as the reference interpreter does, by whoever calls the entry, the MIR driver or native `main`: a value that does not fit traps at the function's name before the entry is called. The entry takes each argument in its parameter's own type and checks the refinements, after every argument is narrowed, as the interpreter does. On every probe and preliminary program that checks, and on programs reaching each construct, the MIR interpreter prints what the reference interpreter prints.

   - `Implemented`: the lowering leaves out of the MIR each bounds and overflow check Tier 1 proves, in refined and unrefined code alike: a narrowing into a plain integer type, an index inside its array, a non-zero divisor, a shift amount in range, and an operation on a 128-bit operand. Each check is matched to the obligations Tier 1 records at the place it records them, a narrowing also by the type the value enters, and is left out only when one exists and every one with that key is proven. An entry's checks, on arguments from outside the program, and the checks a call makes in its callee's scope always stay. On every agent program, over its tasks' examples and hidden tests, the MIR interpreter and native code still print what the reference interpreter prints.
     <!-- @assert-count target="compiler/mente-codegen/src/lower.rs" symbol="fn test_tier1_proofs_leave_bounds_and_overflow_checks_out_of_mir" min="1" reason="Each bounds and overflow check Tier 1 proves is left out of MIR, an unproven one and an entry's stay" -->
   - `Implemented`: it also leaves out each contract check Tier 1 proves: a refinement where a value lands, at an argument or in a `mut` place after the call; a `requires` or `ensures` clause; a written loop `invariant`; and a `decreases` measure, never negative and smaller, in a loop or at a call. Tier 1 tags each obligation with what tells it apart at its place, the clause for a contract clause, every conjunct of an invariant carrying its clause's, so a clause outside the Tier-1 fragment, which records no obligation, keeps its check, in a `@checked` function as in a `@prove` one. A clause whose check is left out is still evaluated, so that a trap inside it stays where the reference interpreter has it. Of a call's checks, made in the callee's scope, only its own are left out: the parameters' refinements, `requires` and the measure, never a check inside a clause's expression.

   - `Specified`: running the MIR beside the reference interpreter on every conformance program.
3. `Specified` **RVSDG canonicalization and Equality Saturation (`E-Graphs`)**:
   - A rewrite pass performs non-destructive algebraic rewrites directly over the `SoA` arrays (e.g., folding identity additions while preserving `ValueLattice` bounds), avoiding phase-ordering cliffs. Neither RVSDG structure nor an e-graph exists yet.
4. **In-memory `MIR` mutation prover**:
   - `Implemented`: `run_in_memory_mutation_gate` flips `Add` ↔ `Sub`, `AddSatQ16` ↔ `SubSatQ16` and `CmpGe` ↔ `CmpLt`, swaps the arms of each `SelectBranchless`, and counts the mutants that the supplied `(inputs, expected)` vectors kill. `mn test --mutate` runs it on one hand-written region with two vectors.
     <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_mutation_gate_counts_survivors" min="1" reason="The gate counts each mutant and the ones the vectors kill" -->
     <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_branchless_integrate_cell_mir_and_mutation_prover" min="1" reason="The demo region's four mutants are all killed" -->
     <!-- @assert-count target="compiler/mente-cli/tests/cli.rs" symbol="fn test_mn_test_mutate_runs_the_demo_gate" min="1" reason="mn test --mutate runs the gate on the demo region" -->
     <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_mutation_gate_flips_each_comparison" min="1" reason="CmpLt and CmpGe flip into each other" -->
   - `Specified`: running it on regions lowered from `.mn` source, with the module's `ensures` contracts and `@example` assertions as the oracle.
   - `Specified` **What passing means**: some mutants cannot be killed by any test because they change nothing observable (an equivalent mutant: flipping `x + 0` to `x - 0`). So the gate does not demand that every mutant die. It passes when every mutant is either killed or marked equivalent with a written reason; `mn test --mutate` lists each survivor with its source line. A project may instead set a kill-rate threshold, and then the report still lists the survivors.
5. **Code generation through Cranelift (Engineering Guardrail #2)**:
   - `Implemented`: `mente-codegen` compiles every MIR function into a Cranelift function, one block for one block, with the source line and column of each instruction, and writes the object with a runtime it generates in Cranelift IR ([`native-runtime`](../docs/design-review.md#native-runtime)): decimal output of integers by 32-bit limbs; 128-bit division, which Cranelift lowers only to 64 bits; checked 128-bit arithmetic and shifts that report the exact value of an overflow below 2^128; for each trap site, the reference interpreter's message on standard error and exit status 1; and a `main` that makes the call its first argument numbers and prints what `mn run` prints. A frame larger than a page touches each of its pages in order on the way down (inline stack probes), as Windows needs to commit its stack and as keeps a frame on any system from jumping over the guard page. It imports only the C library's `write` (`_write` on Windows), `exit` and `memcpy`; a 128-bit value crosses a function boundary as two halves, and a 128-bit result through a pointer the caller passes. `mn` links the object with `cc` on Linux and with MSVC's `link.exe`, found through `vswhere` and the Windows SDK, on Windows. On programs reaching each construct, with a trap of every kind, native code prints what the reference interpreter prints, on each of the three platforms; CI compares the three paths on every agent program's examples and hidden tests.

   - **High-level semantic optimization lives 100% in `MIR`**: Bounds-check elimination (`ValueLattice::proves_in_bounds`), Ghost Contract `Assume` propagation, `AoSoA` (`Tiled<T, lanes: N>`) address calculation, and `@branchless` `SelectBranchless` canonicalization are completed inside `MirRegionSoA` before any target backend runs.
   - **Native code**: `mente-codegen` lowers optimised MIR to Cranelift IR and lets Cranelift emit x86-64 and AArch64 machine code. Cranelift is written in Rust, so no C++ toolchain enters the build; `mente-mir` itself depends on nothing, and only `mente-codegen` depends on Cranelift, and on `gimli` and `object` for its object files and debug information.
   - **What Cranelift does, and what Mente does** (checked against `cranelift-codegen` 0.135.8): Cranelift selects instructions, runs its e-graph mid-end and allocates registers. Mente decides in MIR the two things Cranelift leaves to its user. Inlining: Cranelift performs only the inlines it is asked for, and Mente asks across modules only for `@inline` and generic callees (`holographic-module.md`), and inside a module by a size heuristic. Vectorization: Cranelift has no auto-vectorizer, so `@simd(lanes: N)` loops are lowered to vector operations in MIR.
   - **Vectors are 128 bits wide**: Cranelift's x64 and AArch64 backends handle vector values of at most 128 bits, so `mente-codegen` splits a wider lane group into 128-bit operations (`hardware-contracts.md`).
   - **No floating-point or vector `select` reaches Cranelift from `@branchless` code**, because on x64 Cranelift emits those as a jump around a move. `mente-codegen` lowers a vector select to `bitselect` over a comparison mask and a scalar float select to an integer `select` on the bit pattern; integer selects become `cmov` / `csel`. After emission, `mn` checks each `@branchless` function's machine code (`E0403`, `hardware-contracts.md`).
   - **Errors return as a two-register tagged value**: Cranelift has no flags type and no calling convention that returns a status in the carry flag, so `T ! E` is lowered to a tag and a payload in two return registers through Cranelift's multi-value returns. The Carry-Flag convention of `error-handling-abi.md` is tested later, on a custom emitter or a Cranelift fork.
   - **A backend written in Mente (stage 3)**: the performance stage replaces Cranelift with a native backend written in Mente, for x86-64 and AArch64, as [`long-term-order`](../docs/design-review.md#long-term-order) decided. It becomes the default only when it gives the same results as Cranelift on the whole corpus and neither its generated code, its compile latency nor its debug and profiler information is worse; until then Cranelift is the only backend.
     - `Hypothesis`: its code matches LLVM-compiled equivalents, measured program against program.
   - **SPIR-V** waits for `@kernel`'s execution model (`hardware-contracts.md`).

## 2. Decision rationale and rejected alternatives

| Alternative considered | Reason for rejection |
| :--- | :--- |
| **Writing the native backend from scratch first** | Register allocation, instruction selection and object-file emission for two architectures are years of work before the first example runs natively, and they test none of Mente's own ideas, which all live above MIR. Cranelift supplies them in pure Rust; the backend written in Mente arrives in stage 3, after self-hosting, behind the same MIR. |
| **Upstream C++ `MLIR` / `LLVM` heap object graphs (`mlir::Operation*`)** | Upstream C++ MLIR allocates every operation, attribute, and use-def list as heap-allocated 64-bit pointer-linked C++ objects (120–256 bytes per op), causing severe L1/L2 cache thrashing during optimization passes, adding a multi-gigabyte C++ build dependency, and lacking native per-node refinement interval lattices (`ValueLattice`). |
| **Requiring 100% of mutants killed** | Unreachable in general: an equivalent mutant survives every test, so the rule would push authors to write meaningless tests or to stop running the gate. Accounting for every survivor keeps the gate strict without demanding the impossible. |
| **Source-level file rewriting mutation testing (`cargo-mutants`)** | Mutating `.rs` or `.mn` source files on disk and invoking the full compiler + linker per mutant takes minutes to hours. Mutating `MirOp` values in memory inside `MirRegionSoA` executes in microseconds (34 µs for the demo region's four mutants, measured 2026-11-04). |
