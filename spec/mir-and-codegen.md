# From-Scratch 64-Byte `SoA` Mente IR (`MIR`) and Multi-Backend Codegen

**Governs:** `compiler/mente-mir`, `compiler/mente-codegen`

## 1. Specification

1. `Implemented` **Index-addressed structure-of-arrays region** (`MirRegionSoA`, `compiler/mente-mir/src/lib.rs`):
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_nodes_are_rows_addressed_by_index" min="1" reason="Each node is one row of the parallel arrays, addressed by its NodeId" -->
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_interpreter_compares_and_selects" min="1" reason="The interpreter's comparisons, select and jump" -->
   <!-- @assert-count target="compiler/mente-mir/src/lib.rs" symbol="fn test_branchless_integrate_cell_mir_and_mutation_prover" min="1" reason="The interpreter evaluates a region over its arrays" -->
   - Every `MIR` instruction node is addressed by a 32-bit index handle (`NodeId(pub u32)`, `4` bytes) rather than a 64-bit heap pointer (`8` bytes).
   - `MirRegionSoA` stores one straight-line region in parallel vectors: `opcodes: Vec<MirOp>`, `types: Vec<MirType>` (`I64`, `Q16_16`, `Bool`), `inputs: Vec<[NodeId; 3]>`, `lattices: Vec<ValueLattice>` (an `i128` interval and an alignment per node), `lines: Vec<u32>`, plus `is_branchless_guaranteed: bool` and `ret_node`.
   - `MirOp` today: `Param`, `Const`, `Add`, `Sub`, `AddSatQ16`, `SubSatQ16`, `Shr`, `CmpGe`, `CmpLt`, `CmpEq`, `SelectBranchless`, `BranchCondJump`. There are no loads, stores, calls, loops or nested regions. The region serves the demo of `mn test --mutate`; functions lowered from source use the MIR of the next item.
   - `#[repr(align(64))]` on `MirRegionSoA` aligns the struct header only; the node arrays are ordinary heap `Vec`s.
   - `Specified`: packing nodes into 64-byte cache-line buckets.
2. **MIR as an SSA control-flow graph** (`compiler/mente-mir/src/cfg.rs`, [`mir-control-flow`](../docs/design-review.md#mir-control-flow)):
   - A function is a list of blocks, block 0 its entry, each with parameters, instructions and one terminator: a jump or a branch carrying the target's arguments, a return, or a trap. Its values, instruction results and block parameters alike, are rows of parallel arrays addressed by `NodeId`: operation, type, operands (a range of one shared pool) and source line and column.
   - Types are the integer types by width and signedness, `bool`, and addresses. Arrays live in memory, a stack slot or an address a caller passes, read and written by `load` and `store`; a `mut` parameter is an address too, so a call changes its argument in place.
   - Every value fits its type. An exact operation's operands and result share a type wide enough for its static range (`core-calculus.md` item 4), so it never overflows; a checked one, on `i128` or `u128`, computes its exact result from operands that may keep their own types, an `i32` beside a `u128`, and traps when that result leaves its type. Each run-time check is an instruction of its own, `check`, so a pass can erase one Tier 1 proved, and each trap site carries the message the reference interpreter prints for it.
   - `Specified` **A call's count is an instruction** ([`stack-budget`](../docs/design-review.md#stack-budget)): the lowering writes each call's count against the stack budget (`core-calculus.md`, item 25) as an instruction of its own. It names the callee, adds the callee's frame to the stack in use, and traps where the sum exceeds the budget; the call's return gives the bytes back. It stands after the instructions that evaluate the call's arguments and before the checks that narrow them, so the MIR itself holds item 25's order of traps. It is an instruction, as a `check` is, so that the decision to leave it out is made in MIR (**Engineering Guardrail #2**): where the budget left at the entry of a `@max_stack(n)` call graph covers `n`, the counts inside the graph cannot trap and are not run (`hardware-contracts.md`, item 1). How is the lowering's choice; it may lower such a function twice, with its counts and without, and choose at the entry. The MIR interpreter counts as the instruction says, and its limit on depth goes.
   - `Implemented`: the MIR, a builder, a verifier of operands, types and jump arguments, and an interpreter that runs a function over byte-addressed memory, keeps its call frames on a stack of its own, stops at a depth and a step limit, and reports a trap in the reference interpreter's words; an exact operation that leaves its type is reported as broken MIR, a lowering bug.

   - `Implemented`: the interpreter's memory keeps each slot apart: a load, store or copy that leaves its slot, into the gap before the next one, across its end or past every address, is broken MIR, never a read of a neighbour's bytes or a panic. A call's return gives back the slots made since it began, counted rather than found by address, so that a caller's slot of no bytes, which begins where the call's memory does, stays with its frame. A slot's bytes hold a fill until written, 0 unless a run asks for another, so that a run can show a read of memory nothing wrote, as native code's stack would; a run also gives the instructions it executed.

   - `Implemented`: `mente-codegen` lowers a checked module into this MIR, following the reference interpreter step for step: each operation in a machine type wide enough for its static range, a value narrowed and checked against its refinement where it lands, a call's arguments narrowed and its callee's refinements, `requires` and `decreases` measure checked by the caller, where those traps are located, `ensures` at each return, loop invariants and measures, and every trap the interpreter raises, in its words. Each function also gets an entry, which checks arguments from outside the program as a call does.    - `Implemented`: it also leaves out each contract check Tier 1 proves: a refinement where a value lands, at an argument or in a `mut` place after the call; a `requires` or `ensures` clause; a written loop `invariant`; and a `decreases` measure, never negative and smaller, in a loop or at a call. 5. **Code generation through Cranelift (Engineering Guardrail #2)**:
   - `Implemented`: `mente-codegen` compiles every MIR function into a Cranelift function, one block for one block, with the source line and column of each instruction, and writes the object with a runtime it generates in Cranelift IR ([`native-runtime`](../docs/design-review.md#native-runtime)): decimal output of integers by 32-bit limbs; 128-bit division, which Cranelift lowers only to 64 bits; checked 128-bit arithmetic and shifts that report the exact value of an overflow below 2^128; for each trap site, the reference interpreter's message on standard error and exit status 1; and a `main` that makes the call its first argument numbers and prints what `mn run` prints. A frame larger than a page touches each of its pages in order on the way down (inline stack probes), as Windows needs to commit its stack and as keeps a frame on any system from jumping over the guard page. It imports only the C library's `write` (`_write` on Windows), `exit` and `memcpy`; a 128-bit value crosses a function boundary as two halves, and a 128-bit result through a pointer the caller passes. `mn` links the object with `cc` on Linux and with MSVC's `link.exe`, found through `vswhere` and the Windows SDK, on Windows. On programs reaching each construct, with a trap of every kind, native code prints what the reference interpreter prints, on each of the three platforms; CI compares the three paths on every agent program's examples and hidden tests.
     <!-- @assert-count target="compiler/mente-cli/src/mir_run.rs" symbol="fn test_native_code_runs_each_construct_as_the_reference_interpreter_does" min="1" reason="Native code prints what the reference interpreter prints on each construct" -->
   - `Specified` **Native code and the stack budget** ([`stack-budget`](../docs/design-review.md#stack-budget)):
     - **The check.** The runtime keeps the stack in use (`core-calculus.md`, item 25) in one word of memory. For each count instruction (item 2), native code loads it, adds the callee's frame, compares the sum with the budget and branches to a trap site, which reports `stack-overflow` as every trap is reported; it stores the sum before the call and the old value after it. That is the cost a call shows its reader, and what `@max_stack` removes inside a call graph whose bound fits (`hardware-contracts.md`, item 1).
     - A callee's frame is a fact of its body, which no caller is compiled against (`holographic-module.md`): inside one module it is a constant of the code, and across modules a constant the linker fills in from the callee's object. A `@max_stack` bound is read from the signature.
     - **The real stack.** A machine frame is not item 25's frame. It holds a return address, saved registers, spill slots, padding and the arguments of the function's own calls, and it holds no slot for a value kept in a register. The two are tied by a ratio measured for each program when it is built. For a function `f` compiled into the program, `S(f)` is its frame as item 25 counts it, and `M(f)` its machine frame: the most its code lowers the stack pointer below where its caller's call instruction found it, the return address included. Cranelift gives it with the compiled function, as the frame layout of its code buffer: the offset from the bottom of the frame to the frame pointer, plus the setup area that holds the saved frame pointer and the return address. The unwind information does not give it, since it describes neither stack slots nor spill slots. The program's ratio is the largest `M(f) / S(f)` among its functions, rounded up to a whole number. It exists because every `S(f)` is at least 64.
     - **The ratio has no bound from the structure.** Item 25 counts what a call holds at once, and a machine frame under Cranelift grows with the size of its function: Cranelift merges none of the stack slots it is given, and its register allocator reuses spill slots only in part. Measured on 2026-11-14 with Cranelift 0.137.1 on the three targets, by a counter written for the measurement, before the checker computes a frame: a `match` whose arms each hold a 24-byte value takes 24 bytes of slots an arm, 4,800 at two hundred arms, for a frame that counts 160; and a function of statements that each call takes 2 bytes of spill area a statement on x86-64 and 4 on AArch64, 12,848 bytes at 3,200 statements, with 8 bytes of slots in all. Over every program of the conformance suite, the kernels and the benchmark's agent programs that lowers, the largest ratio was 2.70; for a recursive `match` of fifty arms it was 10.6. The implementation measures again, with the checker's own count.
     - **The ceiling is the compiler's to keep.** The ratio a compiler may reach is 256: a machine frame is at most 256 times its frame. That is an obligation of the compiler, not a rule of the language. A function over it is a limit of the compiler, reported as one when native code is built: the report names the function, says that the compiler cannot build it yet, and says that splitting it avoids the limit. It is never an error of the program: `mn check` and the two interpreters accept the function, and the report says so.
     - **What the native path does not do yet.** Until the compiler keeps the ceiling for every function, one past it is not built for the targets where it is past it, while the interpreters run it. A machine frame differs by target, so a function may build for one target and not for another. That is the one difference between the paths this item leaves, and it is met when a program is built, never while it runs. On the figures above, a frame of 160 bytes passes the ceiling at 40,960 machine bytes, about 1,270 arms of 32 bytes each; and a frame of 128 bytes at 32,768, about 8,000 statements that each call on AArch64, at 4 bytes a statement, and about 16,000 on x86-64, at 2. Two means remove it: slots given by scope and reused, below, and a machine function split where its spill area grows.
     - `mn` reserves for the program's stack the ratio times the budget, plus an allowance for what is on the stack and counts nothing. Under the ceiling, that is never more than 256 times the budget and the allowance, whatever the program; `mn build` and the cost report print it.
     - **The allowance, computed part.** The runtime's own code counts nothing: its `main`, whose frame holds the run's arguments and result; the entries (item 2); and the routines a function of the program calls, for decimal output, 128-bit division, checked 128-bit arithmetic and shifts, and the report of a trap. `mente-codegen` compiles all of them, so it reads each one's machine frame as it reads `M(f)`. They call the program only through the one entry a run calls. For the types the compiler has today, integers, `bool`, arrays, structs and enums, none of which holds itself (`core-calculus.md`, item 13), they do not recurse. So the most they have on the stack is a sum over two chains, which `mn` computes for each program: `main` and the largest entry, above the first call, and the longest chain of routines, below the innermost. `mn` refuses to write an object in which a function has neither a counted frame nor a place in that sum, or in which the runtime's routines call in a cycle, so no routine is added outside the bound.
     - **What the bound does not cover yet.** The routines `List<T>` brings, which free, clone, compare and print a value, descend with data that may nest without end, `struct Node { kids: List<Node> }`; no sum over chains bounds them, and what does is not decided ([`recursive-data-descent`](../docs/design-review.md#recursive-data-descent)). A `dyn` call, which M4 brings, has no one callee for its count to name. And an object `mn build --object` writes for Windows carries no reservation, which there is the linker's option, so a program linked outside `mn` must be given the size `mn build` prints.
     - **The allowance, fixed part.** A fixed figure of 262,144 bytes covers the code `mente-codegen` does not compile and cannot measure: the C library functions the runtime imports, the frames the system puts above `main` or above a thread's start, and what the C library keeps of a thread's stack for itself. The figure is four pages of the largest size a target's system uses, 65,536 bytes on some AArch64 kernels: one for the guard page a C library takes out of a thread's stack, one for the thread's descriptor and static storage, and two for the library's calls. It is checked by test, not by proof, and only for the C libraries of the CI matrix. The reservation as `mn build` computes it cannot show the figure too small, since the ratio is rounded up and multiplies the whole budget, which leaves slack that hides it. So the test builds its programs with a reservation of its own, cut to what the argument below needs: the machine frames of the calls its program has open at its deepest, which the test adds up from the frames `mn build` reports, and the allowance, with nothing over but the rounding of the whole up to a page, the unit a system reserves in. It has a program for each chain the computed part sums, so that each of the runtime's routines is reached from the innermost frame: one that traps there, one that divides 128-bit integers there, one whose checked 128-bit arithmetic overflows there, one that copies an array, and one that returns a result to print, each of which ends in the C library. On each platform they run under that reservation, and again with the fixed figure halved. One that ends at the guard page fails the test. What a pass shows is that the C library took no more than half the figure and what the rounding left, under a page; it shows no more. Under another C library the guard page is what stands behind the figure.
     - **Why the trap comes before the guard page.** Let the calls open at some moment be `f1` to `fk`. Each passed its count, so `S(f1) + ... + S(fk)` is at most the budget. Each `M(fi)` is at most the ratio times `S(fi)`, by the ratio's definition. So the machine frames of the open calls take at most the ratio times the budget; the runtime's code above and below them takes at most the computed part of the allowance; and the whole stack is within the reservation while the C library stays within the fixed part. The count runs in the caller, before its call instruction, so a call that does not fit pushes nothing, not even its return address, and the report of the trap runs in the caller's frame and in routines and C library functions the allowance covers.
     - **Where the stack comes from.** On Windows the linker records the reservation in the executable (`link.exe /STACK`), and pages are committed as the inline probes touch them. On Linux the system's limit, not the executable, sizes the first thread's stack. So the process's `main` only creates one thread with the reservation as its stack size and waits for it, and the runtime's work, the reading of the arguments and the printing of the result included, runs on that thread. A system that refuses the reservation cannot start the executable, as one that cannot load it: the program ends before its first call with a message of its own. Since the ceiling bounds the reservation for every program, that says nothing of the program, and it alone lies outside the comparison of the three execution paths.
     - **What the runtime imports then.** The thread takes five more functions of the C library, on Linux only: `pthread_attr_init`, `pthread_attr_setstacksize`, `pthread_attr_destroy`, `pthread_create` and `pthread_join`. This amends [`native-runtime`](../docs/design-review.md#native-runtime), under which the runtime imports only `write`, `exit` and `memcpy` (Norman, 2026-11-14). The whole list is then `write` (`_write` on Windows), `exit` and `memcpy` on every target, and those five on Linux.
     - **The second line.** The guard page and the inline probes stay, and no longer decide where a program ends. If a fault of the compiler broke the bound above, the program would end at the guard page, as today, with no memory overwritten, and the comparison of the three execution paths would report it.
     - **Slots given by scope and reused.** The bound needs nothing more of the lowering, since the ratio is measured. To bring the ratio down, the lowering ends a slot where the value it holds ends, at the end of a statement, of a block or of a branch, and lay the slots that are never alive together over one stack slot, since Cranelift merges none. MIR then says where a slot ends, and its interpreter gives the bytes back there and reports a use after that end as broken MIR, which guards against the fault this brings, a value read after its slot was given to another. The spill area stays Cranelift's.
     - `mn build` prints the reservation, the ratio and the function that sets it, and the cost report shows them ([`cost-report`](../docs/design-review.md#cost-report)). On request it prints every function's machine frame and the two parts of the allowance, routine by routine, which the allowance's test adds up. The reservation is address space: no page is committed before it is touched.
     - Native code does none of this today: it counts nothing, and the system ends a program that runs out of stack at the guard page (`core-calculus.md`, item 25).

   - **High-level semantic optimization lives 100% in `MIR`**: Bounds-check elimination (`ValueLattice::proves_in_bounds`), Ghost Contract `Assume` propagation, `AoSoA` (`Tiled<T, lanes: N>`) address calculation, and `@branchless` `SelectBranchless` canonicalization are completed inside `MirRegionSoA` before any target backend runs.
   - **Native code**: `mente-codegen` lowers optimised MIR to Cranelift IR and lets Cranelift emit x86-64 and AArch64 machine code. Cranelift is written in Rust, so no C++ toolchain enters the build; `mente-mir` itself depends on nothing, and only `mente-codegen` depends on Cranelift, and on `gimli` and `object` for its object files and debug information.
   - **What Cranelift does, and what Mente does** (checked against `cranelift-codegen` 0.135.8): Cranelift selects instructions, runs its e-graph mid-end and allocates registers. Mente decides in MIR the two things Cranelift leaves to its user. Inlining: Cranelift performs only the inlines it is asked for, and Mente asks across modules only for `@inline` and generic callees (`holographic-module.md`), and inside a module by a size heuristic. Vectorization: Cranelift has no auto-vectorizer, so `@simd(lanes: N)` loops are lowered to vector operations in MIR.
   - **Vectors are 128 bits wide**: Cranelift's x64 and AArch64 backends handle vector values of at most 128 bits, so `mente-codegen` splits a wider lane group into 128-bit operations (`hardware-contracts.md`).
   - **No floating-point or vector `select` reaches Cranelift from `@branchless` code**, because on x64 Cranelift emits those as a jump around a move. `mente-codegen` lowers a vector select to `bitselect` over a comparison mask and a scalar float select to an integer `select` on the bit pattern; integer selects become `cmov` / `csel`. After emission, `mn` checks each `@branchless` function's machine code (`E0403`, `hardware-contracts.md`).
   - **Errors return as a two-register tagged value**: Cranelift has no flags type and no calling convention that returns a status in the carry flag, so `T ! E` is lowered to a tag and a payload in two return registers through Cranelift's multi-value returns. The Carry-Flag convention of `error-handling-abi.md` is tested later, on a custom emitter or a Cranelift fork.
   - **A read-only `?T` crosses a call as an address or none**, for a `?T` over 16 bytes, whether or not `T` has a niche: `mutable-value-semantics.md` (item 1) states the convention once, and native code follows it. So a projection `p?.f` and a `T` held in memory are passed where they lie, and no `?T` is built for a read-only argument (`core-calculus.md`, items 15 and 25).
   - **A backend written in Mente (stage 3)**: the performance stage replaces Cranelift with a native backend written in Mente, for x86-64 and AArch64, as [`long-term-order`](../docs/design-review.md#long-term-order) decided. It becomes the default only when it gives the same results as Cranelift on the whole corpus and neither its generated code, its compile latency nor its debug and profiler information is worse; until then Cranelift is the only backend.
     - `Hypothesis`: its code matches LLVM-compiled equivalents, measured program against program.
   - **SPIR-V** waits for `@kernel`'s execution model (`hardware-contracts.md`).

## 2. Decision rationale and rejected alternatives

| Alternative considered | Reason for rejection |
| :--- | :--- |
| **Writing the native backend from scratch first** | Register allocation, instruction selection and object-file emission for two architectures are years of work before the first example runs natively, and they test none of Mente's own ideas, which all live above MIR. Cranelift supplies them in pure Rust; the backend written in Mente arrives in stage 3, after self-hosting, behind the same MIR. |
| **Upstream C++ `MLIR` / `LLVM` heap object graphs (`mlir::Operation*`)** | Upstream C++ MLIR allocates every operation, attribute, and use-def list as heap-allocated 64-bit pointer-linked C++ objects (120–256 bytes per op), causing severe L1/L2 cache thrashing during optimization passes, adding a multi-gigabyte C++ build dependency, and lacking native per-node refinement interval lattices (`ValueLattice`). |
| **Requiring 100% of mutants killed** | Unreachable in general: an equivalent mutant survives every test, so the rule would push authors to write meaningless tests or to stop running the gate. Accounting for every survivor keeps the gate strict without demanding the impossible. |
| **One fixed stack for every executable, behind a low ceiling on the ratio, such as 8** | Every executable would have one stack size, known without compiling. But a ceiling near real code's ratios refuses real functions, by what the register allocator spills and differently on each target: the fifty-arm `match` of item 5 stands at 10.6. Measuring the ratio costs address space only, and leaves a limit of the compiler at 256, far from real code ([`stack-budget`](../docs/design-review.md#stack-budget)). |
| **A ceiling on the ratio that the structure guarantees** | Only a count that grows with the code as Cranelift's frames do gives one, the sum of all a body ever holds, and that count takes a recursive `match` of fifty arms at a hundred times what it holds at once (`core-calculus.md`, section 2). |
| **A check of the real stack pointer at each call, in place of the count** | It costs the same and needs no ratio, but machine frames differ by target and by the compiler's version, so the three execution paths would trap at different calls (`core-calculus.md`, item 25). |
| **Source-level file rewriting mutation testing (`cargo-mutants`)** | Mutating `.rs` or `.mn` source files on disk and invoking the full compiler + linker per mutant takes minutes to hours. Mutating `MirOp` values in memory inside `MirRegionSoA` executes in microseconds (34 µs for the demo region's four mutants, measured 2026-11-04). |
