# Mente Design Review Ledger

The open problems in Mente's design, found in the review of 2026-11-04, and what is proposed for each. The design is corrected one entry at a time: an entry is decided, the governing `spec/*.md` and the examples are changed to match, and the entry's status moves to `done` with the commit that did it.

The first pass, on 2026-11-04, made the documents say what the compiler does: every `Implemented` label that described a plan was relabelled, names of functions and types that do not exist were removed, and the measured numbers replaced the claimed ones. That pass changed no design decision. The entries below are the design decisions it found; between 2026-11-04 and 2026-11-05 each was decided with Norman and applied in its own commit, except those still marked `proposed` or `open`.

A second review on 2026-11-06 read the design, the examples and `docs/design-brief.md` against the code at `bdffc1c`, and added the `open` and `proposed` entries of sections 1 to 9. The same day Norman set Mente's goal, a general-purpose language for AI agents (section 10), and the long-term order of the work: foundation, self-hosting, performance, new domains (`long-term-order` and the entries after it in section 8). Apart from `long-term-order`, which is `decided`, none of these entries was decided that day; each decision since is recorded in its entry's status, with the date.

Statuses: `open` (not decided), `proposed` (a resolution is written below and waits for a decision), `decided` (agreed, not yet applied), `done` (applied; the commit is named).

## 2. Type system

| Key | Problem | Proposed resolution | Status |

| `units-scale` | `unit ms = 0.001 * sec` has the same dimension as `sec`, and the rule for `+` compares only dimension vectors, so `5.0_ms + 1.0_sec` type-checks and adds raw numbers. Example 01's comment says it converts instead (`9.5_sec + 500.0_ms` is `10.0_sec`). Also unspecified: integer quantities with a non-integer scale (`u64<ms>`), functions generic over a unit, and whether exponents are integers. | A unit is a dimension vector plus a scale. `+`, `-` and comparisons require the same unit, scale included; conversion is explicit (`t.to<sec>()`), so no hidden float multiply appears. A bare `_q16` is not a format. | done: [`surface-syntax.md`](../spec/surface-syntax.md) item 6, [example 02](../examples/02_mechanical_sympathy_simd.mn) (commit "Define literal suffixes and arbitrary-width integers") |
| `bitfield-widths` | `bitstruct` fields use `u4`, `u3` and `u24`, which no spec defines, and the prover does not check a field's type width against its `@bits` range. | Define `uN` / `iN` for `1 <= N <= 128`, and reject a field whose type width differs from its range width. | done: [`morphic-layouts.md`](../spec/morphic-layouts.md) items 3–4, `E0424` / `E0425` in the compiler (commit "Define literal suffixes and arbitrary-width integers") |
| `float-square-ensures` | Example 01's `kinetic_energy` cannot be accepted under the spec. Its `ensures result >= 0.0_joule` is in the Tier-1 fragment by syntax, so `mn check` must prove it, but the clause is false: `vel` is an unrefined `f64`, and `vel = NaN`, or `mass = 0.0` with `vel = inf`, makes the result `NaN`, for which `>=` is false. Even without `NaN`, interval arithmetic on `0.5 * mass * vel * vel` treats the two `vel`s as independent values and cannot prove the product non-negative. There is no way out either: `@checked` would add a trap, which is a branch `@branchless` forbids, and `@prove` needs Tier 2. The spec also does not say whether Tier 1's floating-point intervals round outward, which soundness needs. | Refine `vel` to exclude `NaN` and the infinities (`f64[-3e8..=3e8]<meter / sec>`, which also keeps the result finite), write the body as `0.5 * mass * (vel * vel)`, and give interval arithmetic the rule that a binding multiplied by itself is non-negative; the `@example` then has to show that its `v` lies in range, which Tier 1 gets from the literals. Tier 1's floating-point intervals round outward. `ghost-contracts-and-totality.md` states the general rule: a fragment clause that Tier 1 cannot prove from the body is a compile error, and a `@branchless` function has no `@checked` fallback for it. | proposed |
| `sat-mixing` | Example 02's `integrate_cell` adds a `q16.16` to a value derived from a `sat<q16.16>` (`leaked + drive`), compares the sum with a `q16.16` (`next_v >= cell.threshold`), and assigns an `if` whose arms are a `q16.16` and that sum to a `sat<q16.16>` field. | `combined-scalar-types` | A refinement, a unit and a fixed-point or saturating type can meet in one type (`f64[0.0..=1e12]<kg>`, or `sat<q16.16>` with a unit), but no spec gives the order of the parts, whether an interval's bounds are in the unit's scale, or how interval arithmetic and unit arithmetic combine in one operation. | | open |
| `closure-captures` | Closures are used (an effect variable is written on `fn(T) -> U with E`) but never specified: what a closure captures and in which mode (`val`, `mut`, `own`), whether a closure that captures a `mut` binding may escape its scope or enter a branch of `parallel (...)`, how the Law of Exclusivity treats a capture, and how a closure's effects meet effect variables. | | open |
| `trait-coherence` | No rule says which module may implement a trait for a type (an orphan rule), or what happens when two implementations overlap. Static dispatch through a trait-typed parameter and `dyn Trait` both need exactly one implementation to be found. | | open |
| `error-conversion` | Inside a function returning `T ! E2`, the spec does not say whether `f()!`, where `f` returns `U ! E1`, needs a conversion from `E1` to `E2`, or how such a conversion is written and found. | **Decided (Norman, 2026-11-11):** postfix `!` propagates only the enclosing function's own error type. Inside a function returning `T ! E2`, `f()!` where `f` returns `U ! E1` is an error unless `E1` is `E2`, and its fix converts with `catch`: `f() catch { e => raise E2.Wrap(e) }`. No conversion is implicit. A conversion found by type, as Rust's `?` finds `From`, would hide a call at the propagation site, and needs traits, which come in M4. A shorter explicit form, such as `f()!Wrap`, can be added if the agent benchmark shows agents need it; adding a form is easier than removing one. The strict choice. | decided |
| `overflow-check-cost` | `overflow-release` makes integer and fixed-point arithmetic trap on overflow in every build unless Tier 1 proves it absent. Most checks cost little, since the branch is almost never taken and is well predicted, but in a tight loop a check on every step blocks vectorisation and the reordering of arithmetic, and C and Rust release builds do not pay it at all. Every operator is checked on its own, so an intermediate result traps even when the final value fits: `(lo + hi) / 2`, the overflow that once broke Java's `Arrays.binarySearch`, traps although its result always fits. Nothing in the spec says how the cost is kept down, and the trap is implicitly precise: it happens at the operation that overflowed. | Keep trapping on overflow; making release builds wrap would turn overflow into a silent wrong result, worst of all in code no person reads. Lower the cost with two semantic rules, decided with the core calculus in M0, and four measures. **Rule 1, exact intermediates:** within an expression, intermediate results are computed exactly in a wider integer and checked once, where the value is narrowed to its type: a binding, a store, an argument, a return. This removes checks, one per expression rather than one per operator; it costs nothing for 32-bit and narrower types and for fixed point on 64-bit processors, and little for 64-bit types, whose 128-bit intermediates the hardware supports; it never changes a value a program would have produced, and only turns some traps into the mathematically correct result; and it makes run-time arithmetic match the mathematical integers Tier 1 reasons about. Shifts and bit operations are narrowing points, `wrap<T>` and `sat<T>` keep their own rules, and `i128` falls back to a check per operator. It follows CERT's "As-if Infinitely Ranged" integer model. **Rule 2, imprecise trap regions:** within a region that has no externally visible effect, the remaining checks may be merged and deferred to the region's end, so that a loop accumulates an overflow flag, or a vector loop combines its lanes' overflow masks, and checks once, and vectorisation is not blocked. A trap ends the program, so memory written before it that no one has seen is unobservable; a region therefore ends before every externally visible effect: an effect operation, an FFI call, or a write another task can see (`Shared<T>`, atomics, `Channel.send`). Mente's effects and the Law of Exclusivity tell the compiler where those are, which a C compiler cannot know; Ada's standard grants a similar freedom to move language-defined checks (RM 11.6). Together the two rules say: a value traps only when it must fit a type and does not, at its narrowing point or before it becomes visible. A trap then names its region rather than its operation, and replaying the same input on the reference interpreter finds the operation; the three-way differential counts a trap anywhere in the same region as agreement. `@branchless` is unchanged, since a deferred check is still a branch. The four measures: (1) from M1, Tier 1's intervals remove checks in all code, refined or not, as an optimisation rather than an obligation, so `gradual-verification` holds; (2) loop versioning and checks hoisted out of loops, in MIR from M5 and deeper in stage 3, where one test before a loop selects an unchecked version when the whole loop provably cannot overflow; (3) from M2, `cost-report` gives each check left in a hot path the contract or refinement that would remove it, a prescription an agent can apply where a person would not bother; (4) the cost is measured as a figure of its own from M1 (`performance-stage`). What can be neither proven nor merged keeps its check, and code that wants no check writes `wrap<T>` or `sat<T>`. Deciding this entry changes `refinement-and-fixed-point.md` item 5 to say when and where a trap occurs. **Amended when decided (2026-11-08): exact intermediates beyond 128 bits.** Rule 1 as written assumes every intermediate fits a 128-bit integer, but a product of three `u64` values can reach about 2^192, and only `i128` was given a fallback. So: an operation whose range, computed from the static types alone, may not fit in 128 bits is itself a narrowing point, where the exact result is checked against its operands' type, as it would be without Rule 1. Rule 1's guarantee still holds (no value a program would have produced changes; some traps become the mathematically correct result), and where a check falls depends only on the types, never on run-time values, so it stays deterministic and predictable. | done: [`refinement-and-fixed-point.md`](../spec/refinement-and-fixed-point.md) item 5 (Norman, 2026-11-08, with the amendment to Rule 1 at the end of the resolution; commit "Apply the decisions made before M0 to the roadmap, the spec and the brief") |
| `integer-conversions` | Under exact intermediate results ([`overflow-check-cost`](design-review.md#overflow-check-cost)), `val x: u8 = a + b` is checked at the binding. Whether `val x: u8 = y`, with `y` a `u32`, needs an explicit conversion was not said. | No conversions between integer types: an integer value is a mathematical integer and an integer type names a range, so any integer expression flows into any integer type and is checked where it is narrowed. A plain type is a range checked at run time where Tier 1 cannot prove it; a refined type is a range proven at compile time. Wrapping and saturation stay explicit (`wrap<T>`, `sat<T>`). | done: [`core-calculus.md`](../spec/core-calculus.md) item 2 (Norman, 2026-11-08; commit "Write the core calculus of M1") |
| `integer-inference` | With integers as mathematical values, `u8 + u32` is well defined, but an unannotated binding such as `val s = a + b` still needs a type, and none was specified. | When an expression's integer operands share a type, an unannotated binding takes it (`u8 + u8` is a `u8`, trapping above 255 at the binding); a literal takes its neighbours' type, and literals alone are `i64`; when the operands' types differ, the binding states its type, and the diagnostic suggests the smallest standard type that holds both ranges. | done: [`core-calculus.md`](../spec/core-calculus.md) item 5 (Norman, 2026-11-08; commit "Write the core calculus of M1") |
| `no-shadowing` | Whether a name may be declared again in the same function (`let x = x + 1` in Rust) was not said; refinement bounds name bindings, so a second binding of the same name would make a bound ambiguous to read. | A name is declared once in a function, its parameters and inner blocks included; a second declaration is an error whose fix suggests a new name. | done: [`core-calculus.md`](../spec/core-calculus.md) item 6 (Norman, 2026-11-08; commit "Write the core calculus of M1") |
| `struct-enum-syntax` | `grammar.md` reserves `struct` and `enum` but gives them no rule, and `algebraic-types-and-null.md` reads declarations as raw text. Open: positional payloads (`Deposit(i64)` in the benchmark) beside named ones (`UpstreamFailure(code: u16)` in example 03); a struct literal `Name { f: e }`, ambiguous after `if c`, `while c` and `match x`; places with `.field`; qualified variants (`GatewayError.InvalidToken`) and how `a.b` resolves; field defaults; recursive types. | **Decided (Norman, 2026-11-11):** a struct is built by a call-like form with named fields, `Pair(i: 0, j: 1)`, and an enum's payload fields are always named, built and matched the same way, `Deposit(amount: 5)`: one form, with no ambiguity after a condition. Variants are qualified by their enum's name. A type that contains itself other than through a `List` is an error. Field defaults, places with `.field` and the resolution of `a.b` are written into the grammar with M2's design closure ([`m2-design-closure`](design-review.md#m2-design-closure)). The strict choice over `Name { f: e }` restricted in conditions (Rust) and over a parse that depends on name resolution. | decided |
| `match-patterns` | `algebraic-types-and-null.md` says only that `match` is exhaustive. Undefined: the arm syntax; the pattern forms (bindings, literals, ranges, `_`, `none`, or-patterns, guards, nesting); whether a binding copies or projects the payload; whether `_` may cover variants; exhaustiveness over refined integers and `?T`; and whether an arm no value reaches is an error. | **Decided (Norman, 2026-11-11):** M2's patterns are qualified variants with named bindings, `none`, and integer and `bool` literals, with no guards. `_` never covers an enum's variants, so adding a variant makes every `match` on the enum name it. Exhaustiveness reads refinement ranges: `u8[0..3]` is covered by `0`, `1` and `2`. An arm no value reaches is an error, and a binding is a read-only projection of the payload. The strict choice over Rust's full patterns, which a later milestone may add. | decided |
| `optional-semantics` | `algebraic-types-and-null.md` defines `?T` as equivalent to `T | none`, which flattens `??T`: `pop` on a `List<?i32>` could not tell an empty list from a stored `none`. The examples turn a `T` into a `?T` implicitly, against "no implicit conversions" (`philosophy.md`). Unstated: how `none` is typed, the narrowing of a `var` or a field path, the `guard val v = opt` form, and whether `A | B` is in M2. `pool[mut h]?.field = v` silently does nothing when `h` is stale (`regions-and-pools.md`). | **Decided (Norman, 2026-11-11):** `?T` is a tagged type and does not flatten: `??T` is a type of its own. A `T` becomes a `?T` only where a value lands in a place of that type, at the narrowing points of `core-calculus.md` (a binding, an argument, a return), as an integer narrows. Union types `A | B` wait past M2. `?.` only reads: a write narrows first with `guard`, so a write through a stale handle never silently does nothing. The narrowing of `var`s and field paths and the `guard val` form are written into the core calculus with M2's design closure. The strict choice over Swift's writes through `?.`, and over flattening, which is unsound for generic code. | decided |
| `error-union-semantics` | Beyond [`error-conversion`](design-review.md#error-conversion), `error-handling-abi.md` leaves open whether a binding, a field or a type argument may hold a `T ! E`; whether a call handled by neither `!` nor `catch` is an error, and whether `_ = f()` may drop an error; what `catch` attaches to, whether it has one binding or arms, and what it must give; whether `raise` is an expression of no value (example 03 writes `else raise ...` without braces); which types `E` may be; and how a function fails without a value. | **Decided (Norman, 2026-11-11):** `T ! E` is a return form only, never the type of a binding, a field or a type argument. Every call of a function that can fail is handled by `!` or `catch`, and `_ = f()` drops no error. `catch` takes arms over `E`'s variants, exhaustive as `match`'s, each giving a `T` or leaving; `raise` is an expression of no value. `E` is a nominal `enum`. Precedence, a function that fails without a value, and the size of `E` under the two-register return (the spike before M2) are written into the spec with M2's design closure. The strict choice over a first-class result type with a must-use rule. | decided |
| `str-text-model` | `str` is a view of UTF-8 text (`regions-and-pools.md`, item 2), but nothing says whether `.len` counts bytes or characters, whether `s[i]` exists, what a slice that cuts a character does, or whether validity is guaranteed. There are no character or byte literals (`'` is `E0105`) and no `\r`, `\0` or `\xNN` escapes, and `==` is defined only on integers and `bool`, while benchmark tasks compare text and characters. | **Decided (Norman, 2026-11-11):** a `str` is always valid UTF-8 and its `.len` counts bytes. It has no `s[i]`: bytes are read through an explicit `[]u8` view. A slice whose bounds cut a character traps, unless Tier 1 proves they fall on boundaries. Byte literals `b'x'` and the missing escapes are added, and `==` compares text byte by byte. Rust's model, chosen over Go's bytes without validity and over a `char` type, which a later milestone may add. | decided |
| `slice-ranges` | Range indexing `x[a..b]`, `..=` and open ends are undefined, with their traps and Tier-1 obligations. Example 01 passes an array where `[]i64` is expected, an implicit conversion against `philosophy.md`, and `String` to `str` or `List<T>` to `[]T` is unstated. A refinement bound may read only an array's `.len` (`core-calculus.md`), yet example 01 bounds a result by a slice's. | **Decided (Norman, 2026-11-11):** an owner becomes a view only explicitly, `xs[..]`, and a sub-range writes both ends, `xs[a..b]`, exclusive of `b`. The strict choice over implicit conversion at arguments and open-ended ranges. | decided |
| `list-string-m2` | M2 adds `List<T>` and `String`, but user generics and traits come in M4 and the standard library in M6. Unstated: whether both are compiler-known types; the method-call grammar (`grammar.md` has only `.ident` after an expression) and static calls (`String.from`); their minimum operations; growth and capacity; what an allocation failure does; and `==` on structs, enums, `?T` and lists. | **Decided (Norman, 2026-11-11):** `List<T>` and `String` are compiler-known types with a closed set of operations listed in one spec item: explicit construction, `push`, `pop` giving `?T`, reading and writing an element with its bounds trap, `swap`, and slicing. A full list doubles its capacity, which the cost report shows, and an allocation that fails traps with a kind of its own. `==` applies to plain types ([`copy-and-drop`](design-review.md#copy-and-drop)) and to text. The strict choice over bringing generics forward to write them in Mente. | decided |

The strict choice over invariants proven at every store and `mut` projection, or checked at run time where unproven. | decided |
