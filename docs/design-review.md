# Mente Design Review Ledger

The open problems in Mente's design, found in the review of 2026-11-04, and what is proposed for each. The design is corrected one entry at a time: an entry is decided, the governing `spec/*.md` and the examples are changed to match, and the entry's status moves to `done` with the commit that did it.

The first pass, on 2026-11-04, made the documents say what the compiler does: every `Implemented` label that described a plan was relabelled, names of functions and types that do not exist were removed, and the measured numbers replaced the claimed ones. That pass changed no design decision. The entries below are the design decisions it found; between 2026-11-04 and 2026-11-05 each was decided with Norman and applied in its own commit, except those still marked `proposed` or `open`.

Statuses: `open` (not decided), `proposed` (a resolution is written below and waits for a decision), `decided` (agreed, not yet applied), `done` (applied; the commit is named).

## 1. Interface and modularity

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `interface-from-signature` | `spec_hash` promises that a body edit never recompiles dependents, but three designs read bodies at the interface: return-slice provenance inferred from the body (`regions-and-pools.md` §1), whole-program stack sizing for fibers (`structured-concurrency.md` §2), and bodies that dependents instantiate or inline (generic functions under static-default traits, `comptime` functions, small `@branchless` helpers). Each makes a body edit change what dependents compile against. | Everything a dependent compiles against is written in, or derived from, the signature alone. Provenance: a conservative default (a returned view may borrow from every read-only or `mut` view parameter) narrowed by an optional `from p` clause in the signature. Fibers: see `fiber-stacks`. Instantiable bodies: hash them into a third digest that only instantiating dependents depend on. | done: `holographic-module.md` §2–3, `regions-and-pools.md` §1, `instance_hash` and the `from` clause in the compiler (commit "Read every interface fact from the signature") |

## 2. Type system

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `units-scale` | `unit ms = 0.001 * sec` has the same dimension as `sec`, and the rule for `+` compares only dimension vectors, so `5.0_ms + 1.0_sec` type-checks and adds raw numbers. Example 01's comment says it converts instead (`9.5_sec + 500.0_ms` is `10.0_sec`). Also unspecified: integer quantities with a non-integer scale (`u64<ms>`), functions generic over a unit, and whether exponents are integers. | A unit is a dimension vector plus a scale. `+`, `-` and comparisons require the same unit, scale included; conversion is explicit (`t.to<sec>()`), so no hidden float multiply appears. Exponents are integers. Unit parameters: `fn mean<comptime U: Unit>(xs: []f64<U>) -> f64<U>`. Scaling an integer quantity by a non-integer factor is an error. | done: `dimensional-units.md` §2–5, example 01 (commit "Give units a scale, and make conversion explicit") |
| `interval-subtyping` | The rules for entering and leaving a refined type are missing: whether `u32[0..10]` is a subtype of `u32`, how a literal or an arithmetic result gets an interval, and what `usize[0..items.len]` means while `items` is a `var` whose length can change. | A refined type is a subtype of its base type. A value enters a refinement by a literal in range, an interval-arithmetic result, or a `guard`. A refinement may name only bindings that are immutable for the refinement's whole scope. | done: `refinement-and-fixed-point.md` item 1 (commit "Say how values enter refinements, and trap on overflow everywhere") |
| `octagon-midpoint` | The specified Tier 1 (intervals plus octagons, `±x ± y ≤ c`) cannot prove example 01's `val mid: usize[0..items.len] = lo + (hi - lo) / 2`: the `/ 2` gives a coefficient octagons cannot hold, so the relation `mid < hi` is lost. The flagship example is outside the flagship solver. | Tier 1 uses callee contracts modularly, and the standard library provides `midpoint(lo, hi)` with `requires lo < hi` and `ensures lo <= result and result < hi`; example 01 calls it. Widening Tier 1 to general linear arithmetic would lose its predictability guarantee. | done: `ghost-contracts-and-totality.md` §4, example 01 (commit "Prove binary search through midpoint's contract") |
| `requires-fragment` | An unproved `requires` is a compile error, and Tier 1 only understands intervals and octagons, so a function whose precondition is outside that fragment (`requires is_sorted(items)`) can be called only where Tier 2 runs, and Tier 2 is a separate `mn prove` step. | Classify each clause by syntax. A Tier-1-fragment clause is checked by `mn check`. Any other clause needs the function marked for `mn prove`, or is declared `@checked` and compiled to a runtime check. | done: `ghost-contracts-and-totality.md` §2, `E0503` (commit "Classify contract clauses by the tier that proves them") |
| `generic-angle-ambiguity` | `parse<i32>(input)` without turbofish is claimed to be settled by "LL(k)", but `f(a < b, c > (d))` stays ambiguous. No rule is written. | Adapt C#'s rule: a `<...>` that parses as type arguments is taken as type arguments only when the token after `>` is one of `(`, `)`, `[`, `]`, `}`, `:`, `,`, `.`, `?`, `==`, `!=`; otherwise it is a comparison. So `f(a < b, c > (d))` calls `a<b, c>` with `d`, as in C#. | done: `traits-and-generics.md` §1 (commit "One spelling for slices, compile-time parameters and generic calls") |
| `overflow-release` | Integer and fixed-point overflow is checked "in debug/verification modes"; release behaviour is unspecified, which leaves room for silent wrap or undefined behaviour. | Default arithmetic traps on overflow in every build unless overflow is proven absent; wrapping and saturation are only through `wrap<T>`, `sat<T>` and their operators. `@branchless` code needs the proof, since a trap is a branch. | done: `refinement-and-fixed-point.md` item 5 (commit "Say how values enter refinements, and trap on overflow everywhere") |
| `string-types` | `str` is used as a view (example 03 returns a slice of its parameter) and as stored text (example 04's `SceneNode.name`), and no owned string type exists. | `str` is a view; an owned, growable `String` is added; storing a `str` in a struct follows the provenance rules. | done: `regions-and-pools.md` item 2, example 04 (commit "Separate views from owned text, and make pool indexing ?T throughout") |
| `comptime-params` | Compile-time parameters have three spellings: `<T, const CAP: usize = 64>` (example 01), `<comptime T: Type>` (`comptime-and-ffi.md`), and plain `<T>` (example 04). The spec's example also uses `val item: T` as a parameter mode, which `mutable-value-semantics.md` does not define. | One spelling: a bare `T` in `<...>` is a type parameter, and a compile-time value is `comptime N: usize`. Parameter modes stay the four in `mutable-value-semantics.md`. | done: `traits-and-generics.md` §1, `comptime-and-ffi.md`, example 01 (commit "One spelling for slices, compile-time parameters and generic calls") |
| `pool-indexing` | `regions-and-pools.md` says `pool[h]` returns `?T` and `pool.get_mut(h)` gives a `mut` projection; example 04 writes `pool[mut h].children.push(...)` and reads `scene[root].children.len` as a plain `T`. | Pick one. Proposed: `pool[h]` is `?T`, the `mut` projection is `pool[mut h]` (also `?T`), and example 04 narrows with `guard`. | done: `regions-and-pools.md` item 4, example 04 (commit "Separate views from owned text, and make pool indexing ?T throughout") |
| `slice-syntax` | Slices are `[]T` in the examples and `Slice<T>` in the specs; `comptime-and-ffi.md` alone uses `Slice<u8>[len: 1..=MAX]`, a refinement on a length that no other spec defines. | `[]T` for slices and `[N]T` for arrays, as the examples and the `@layout` prover use; length refinements get one defined form. | done: `refinement-and-fixed-point.md` item 2 and every spec (commit "One spelling for slices, compile-time parameters and generic calls") |
| `literal-suffixes` | Literals such as `200.0_meter`, `0.5_q16` and `0.0_q1_15` appear in the examples; no spec defines the suffix grammar, and `_q16` does not say which `q` format it means. | Define the grammar: `<number>_<unit>` for units, and `<number>_q<I>_<F>` for fixed-point, writing the type name's dot as `_` so the literal stays one token (`0.5_q16_16`; example 02 already writes `0.0_q1_15`). A bare `_q16` is not a format. | done: `surface-syntax.md` item 6, example 02 (commit "Define literal suffixes and arbitrary-width integers") |
| `bitfield-widths` | `bitstruct` fields use `u4`, `u3` and `u24`, which no spec defines, and the prover does not check a field's type width against its `@bits` range. | Define `uN` / `iN` for `1 <= N <= 128`, and reject a field whose type width differs from its range width. | done: `morphic-layouts.md` items 3–4, `E0424` / `E0425` in the compiler (commit "Define literal suffixes and arbitrary-width integers") |

## 3. Memory model

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `mut-projection-soa` | A `mut` parameter lowers to a `T* restrict` pointer, but an element of `SoA<T>` or `Tiled<T, lanes>` is not a contiguous `T`, so `step(mut particles[i])` and `parallel_for p in mut batch` over a `Tiled` have nothing to point to. | Define `mut` by copy-in/copy-out (Swift `inout`, Hylo): the callee sees exclusive access to a value, and passing a pointer is an optimisation for contiguous storage. A `SoA`/`Tiled` element projection gathers into a temporary and scatters back. | done: `mutable-value-semantics.md` item 4, `morphic-layouts.md` §1 (commit "Define mut by copy-in/copy-out") |
| `shared-upgrade` | `Shared<T>` counts non-atomically while thread-local and "upgrades to atomic when transferred". Other clones left in the first thread keep updating the same counter non-atomically while the second thread updates it atomically: a data race. | Either biased reference counting (an owner-thread counter plus a shared atomic counter), or two types: a thread-local count and an atomic one, with `own` transfer across threads requiring the atomic one. | done, as two types: `regions-and-pools.md` item 5, `E0320` (commit "Split Shared<T> into task-bound Local<T> and atomic Shared<T>") |
| `arena-concurrency-and-drop` | Example 03 passes the same `in arena` to both branches of `parallel (...)`, so two tasks bump-allocate in one arena at once; and `in` acts as a mutable use of the arena, which the Law of Exclusivity forbids across concurrent siblings. The `O(1)` reset also skips destructors of arena values that own files or sockets. | `in arena` is a shared allocation capability: the arena allocates atomically, or each branch gets a child arena. Types with a destructor cannot be allocated in an arena, or their destructors run at reset and the reset is no longer `O(1)`. | done, with a chunk per task and no destructors in arenas: `regions-and-pools.md` item 3, `E0312`, example 03 (commit "Give each task its own arena chunk, keep destructors out of arenas") |
| `parallel-exclusivity` | Children of `parallel (...)` may read parent bindings, but nothing forbids one branch from mutating what a sibling reads. | The Law of Exclusivity applies across the branches of one `parallel (...)`, as across the arguments of one call. | done: `structured-concurrency.md` item 3 (commit "Give each task its own arena chunk, keep destructors out of arenas") |
| `layout-alignment-endianness` | A `@layout` struct is claimed bit-identical across targets, but the prover requires neither natural alignment of each field nor a byte order, so a `u64` at byte 4 or a little/big-endian difference passes. | Each `@bytes` start must be a multiple of the field's natural alignment unless the struct says `@packed`; byte order is little-endian unless `@endian(big)` is given. | done: `morphic-layouts.md` item 2, `E0418` / `E0419` in the compiler (commit "Check field alignment in @layout, and fix its byte order") |

## 4. Effects and concurrency

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `effect-polymorphism` | "Colorless" concurrency says `items.map(f)` accepts pure and `with Net` functions alike, but an effect set in the signature is a colour unless `map` can be generic over its argument's effects. Nothing specifies that. | Effect variables: `fn map<T, U, E>(xs: []T, f: fn(T) -> U with E) -> List<U> with E`. | done: `capability-effects.md` item 4 (commit "Rename algebraic effects to capability effects; with declares, handle installs") |
| `with-overloaded` | `with` means three things: an effect clause (`with Net, Clock`), installing handlers (`with Clock = VirtualClock(...) { }`), and opening an arena (`with Arena.scoped() as arena { }`). The specs also use `handle` blocks, `Arena.scoped(capacity) { arena => ... }`, and handler names (`SimClock`, `SimNet`) that differ from the examples' (`VirtualClock`, `MockNet`). | One meaning per keyword: `with` in a signature declares effects, and one block form installs handlers. Whether an arena is a handler of an allocation effect, or its own block form, is to decide. | done: `with` only declares, `handle` installs handlers, and an arena keeps its own `Arena.scoped` block rather than becoming a handler; `capability-effects.md`, example 03 (commit "Rename algebraic effects to capability effects; with declares, handle installs") |
| `handler-semantics` | The spec is titled algebraic effects, but it never says whether handlers are user-defined or whether they capture resumable continuations. Static monomorphisation to direct syscalls only holds for handlers that resume at once. | Handlers are capability implementations that resume immediately (tail-resumptive); no first-class continuations. The spec is renamed to match. | done: the spec is now `capability-effects.md` (commit "Rename algebraic effects to capability effects; with declares, handle installs") |
| `dst-scheduling` | Deterministic simulation needs the order of tasks, fibers and `parallel_for` workers to be deterministic too, but only `Clock` and `Net` are intercepted. | Scheduling is an effect with a deterministic, seeded handler under `mn test`. | done: `capability-effects.md` item 6 (commit "Rename algebraic effects to capability effects; with declares, handle installs") |
| `disjoint-proof-tier` | Found while re-cutting the roadmap. `disjoint-parallelism.md` says the compiler proves index-arithmetic partitions disjoint (`scores[i * S .. (i + 1) * S]`), and its title says SMT, but Tier 1 is intervals and octagons, which cannot hold `i * S`, and Tier 2 runs only under `mn prove`. | Partitions from `.chunks_mut(N)`, `.split_at_mut(mid)` and `Tiled` tiles are disjoint by construction and need no proof. An index-arithmetic partition needs `@prove` on the function (Tier 2), as `requires-fragment` routes any clause outside Tier 1. Retitle the spec. | proposed |
| `fiber-stacks` | Fiber frames are sized by whole-program call-graph analysis, which breaks under separate compilation, `dyn` calls, FFI and recursion, and puts callee bodies into the caller's interface. | Stackful fibers on reserved virtual-memory stacks with guard pages, committed on demand; `@max_stack` stays an opt-in contract for embedded code. | done, as part of `interface-from-signature`: `structured-concurrency.md` §2 |

## 5. Hardware contracts

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `branchless-definition` | "No conditional jump anywhere" also forbids every loop (its back-edge is a conditional branch), every bounds, overflow or division check, and calls that branch inside. Lowering `if` to a select also evaluates both arms, which may trap. | `@branchless` means no conditional branch whose condition depends on data: loops need a compile-time trip count and are unrolled, every check must be proven away, callees must be `@branchless` or inlined, and both arms of a lowered `if` must be total and effect-free. | done: `hardware-contracts.md` item 1 (commit "Define @branchless as no data-dependent branch") |
| `simd-kernel-model` | The example writes `@simd(width: 16)` on a function; the spec writes `@simd(lanes: N)` on a loop. `@kernel` has no execution model (index space, memory spaces, barriers), and example 02 nests `parallel_for` inside `@kernel @simd`, three levels of parallelism with no defined relation. | Define the kernel model before keeping `@kernel` in the language; until then, label it `Hypothesis`. One `@simd` form. | done: `@simd(lanes: N)` on loops only, `@kernel` relabelled `Hypothesis` and removed from example 02 until it has an execution model (commit "Put @simd(lanes: N) on loops, and make @kernel a hypothesis") |
| `transitive-contracts` | `@no_alloc`, `@max_stack` and `@total` are transitive over the call graph, which `dyn` calls, FFI and recursion leave open. | Traits and `extern` declarations carry the contracts their implementations must meet; recursion is rejected in a `@max_stack` call graph and needs a `decreases` measure under `@total`. The `@max_stack` part was applied with `interface-from-signature` (`hardware-contracts.md` §1); the rest is open. | done: `hardware-contracts.md` item 1, `ghost-contracts-and-totality.md` item 3 (commit "Compose @no_alloc and @total from signatures, through traits and FFI") |

## 6. Error ABI

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `cf-abi-scope` | The Carry-Flag ABI carries the error payload in one register, but nothing says what happens when `E` is larger. An epilogue's `add rsp, N` clobbers `CF` before `ret`. SPIR-V has no carry flag. Function pointers and C callers need to know the convention. The rationale compares against a 24-byte `Result` forced onto the stack, while a fair comparison is Rust's two-register `Result` for a payload that fits one register. | Keep it as a `Hypothesis` with a benchmark against the two-register `Result`. Specify: payloads over 8 bytes are returned through memory with `CF` still the tag; epilogues use flag-preserving instructions; `@kernel` and `extern "C"` use a tagged return; function types carry the convention. | done; the speed claim stays a `Hypothesis` until the benchmark runs: `error-handling-abi.md` item 2 (commit "Bound the Carry-Flag ABI, and compare it with the fair alternative") |

## 7. Verification and tooling

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `mutation-kill-rate` | `mir-and-codegen.md` requires 100% of mutants killed. Equivalent mutants (a flip that changes nothing observable) make that unreachable in general. | A kill-rate threshold, with surviving mutants reported and individually marked equivalent. | done: `mir-and-codegen.md` item 3 (commit "Account for every mutant, bound comptime, and keep FFI failures as errors") |
| `mn-bind-scope` | `mn bind` is to add non-null refinements automatically, but C headers do not say which pointers may be null; it is to read `crate.rlib`, which carries no C-ABI description; and parsing real C headers without libclang (C++) is a project of its own. | Pointers are nullable unless annotated (`_Nonnull`, or a Mente sidecar file). Rust libraries are bound through a header generated by cbindgen. The C parser's scope is written down before the feature is promised. | done: `comptime-and-ffi.md` item 2 (commit "Account for every mutant, bound comptime, and keep FFI failures as errors") |
| `ffi-boundary-failure` | Inbound FFI values are boundary-checked, but the spec does not say what happens when a check fails, and raw C pointers have no Mente type. | A failed inbound check is an error value of the `extern` function's return type; raw pointers get a type usable only inside `extern` quarantine. | done: `comptime-and-ffi.md` item 2 (commit "Account for every mutant, bound comptime, and keep FFI failures as errors") |
| `comptime-termination` | `comptime` code is pure, but nothing stops it from looping forever, so a build can hang. | A step budget per `comptime` evaluation, raised explicitly. | done: `comptime-and-ffi.md` item 1, `E0701` (commit "Account for every mutant, bound comptime, and keep FFI failures as errors") |
| `assert-substring` | An `@assert-count` on a `.mn` file is satisfied by a comment, since neither `mn spec` nor `spec-guard` knows `.mn` comment syntax (`spec-guard` warns about this). A directive proves a name exists, never that it behaves. | Behaviour claims cite a unit test by name; directives on `.mn` files are used only for the examples' spelling. Teach `spec-guard` the `.mn` comment syntax in Phase 0. | done in `mn spec`, which strips `.mn` comments; teaching `spec-guard` the same is Phase 0 step 0.25 (commit "Keep comments from satisfying directives on .mn files") |

## 9. Backend (Cranelift)

Found when checking what Cranelift, chosen in `roadmap-scope`, can and cannot do. Checked against the source of `cranelift-codegen` 0.135.8 on 2026-11-05; the latest release, 0.137.1, was not checked.

| Key | Problem | Proposed resolution | Status |
| :--- | :--- | :--- | :--- |
| `cranelift-simd-width` | Cranelift's x64 and AArch64 backends accept vector values of at most 128 bits: `rc_for_type` in `isa/x64/inst/mod.rs` and `isa/aarch64/inst/mod.rs` returns `CodegenError::Unsupported` for anything wider, although the IR's type system names `F32X16`. Its AVX-512 settings (`has_avx512vl`, `has_avx512dq`, ...) only select EVEX encodings for 128-bit operations. So `Tiled<Particle, lanes: 16>` of `f32` runs as four 128-bit operations, not one 512-bit `ZMM` operation as example 02's comment and `morphic-layouts.md` say. The cache-line benefit is unaffected: a 16-lane tile's `f32` field is still exactly one 64-byte line. | `@simd(lanes: N)` counts lanes, not register width: the backend splits `N` lanes into as many native vector registers as it needs, and the contract (no loop-carried dependency, no scalar fallback) still holds. `mente-codegen` emits 128-bit vector operations for Cranelift. 256- and 512-bit registers come only with a backend that supports them (the custom emitter under "Later, unscheduled"). Correct example 02's comment and `morphic-layouts.md` §1 to match. | proposed |
| `cranelift-float-select` | On x64, Cranelift emits a `select` of a floating-point or vector value as `XmmCmove`, which `isa/x64/inst/emit.rs` writes as a conditional jump around a move; `inst.isle` notes that `XmmCmove` "uses jumps". Integer `select` becomes `cmov`, and AArch64 uses `csel`. A `@branchless` function with an `if` over floats would therefore get a data-dependent branch on x64, breaking the guarantee `hardware-contracts.md` gives. | In `@branchless` code, `mente-codegen` never hands Cranelift a floating-point or vector `select`: a vector select becomes `bitselect` over a comparison mask, and a scalar float select goes through an integer bitcast and an integer `select`. Because the guarantee is a hard one, `mn` also checks the result: it disassembles each `@branchless` function's emitted code and rejects any conditional jump, naming the source line (a new `E04xx`). | proposed |
| `cranelift-cf-abi` | Cranelift's IR has no flags type, and none of its calling conventions (`Fast`, `Tail`, `SystemV`, `WindowsFastcall`, `AppleAarch64`, `Probestack`, `Winch`, `PreserveAll`) returns a status in the carry flag; `uadd_overflow` and its kin return the flag as an `i8` value. The Carry-Flag ABI therefore cannot be expressed on stock Cranelift, and the Phase 3 item that implements "both the Carry-Flag and the two-register tagged return" would need a fork of Cranelift. | Phase 3 uses the two-register tagged return, which Cranelift's multi-value returns express directly and which the `extern "C"` wrappers need anyway. The Carry-Flag experiment moves to "Later, unscheduled" with the custom emitter, or is run on a Cranelift fork with a new calling convention; which one is decided when it is scheduled. `error-handling-abi.md` stays a `Hypothesis` either way. | proposed |
| `cranelift-optimizer-scope` | Cranelift has no auto-vectorizer, and inlining is "a library" (`inline.rs`): `Context::inline` performs an inline only when the frontend's `Inline` implementation asks for it, with no heuristics of its own. Nothing in Mente's specs says who makes these decisions. | Mente decides both, in MIR. Inlining across modules happens only for `@inline` and generic functions, as `holographic-module.md` already allows, with a size heuristic inside a module; vectorization comes only from `@simd(lanes: N)` loops, which MIR lowers to vector operations itself. Cranelift is relied on for instruction selection, its e-graph mid-end and register allocation. | proposed |
